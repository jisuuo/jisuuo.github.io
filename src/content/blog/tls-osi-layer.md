HTTP 요청이 서버에 도착하는 과정을 정리하면서 한 가지 의문이 생겼다.

HTTP는 응용 계층(L7), TCP는 전송 계층(L4)에 해당한다. 그렇다면 HTTP 요청을 암호화하는 TLS는 어느 계층에 속할까?

처음에는 TLS의 역할이 암호화이므로 표현 계층(L6)이라고 생각했다. 하지만 실제 HTTPS 통신에서는 TLS가 HTTP와 TCP 사이에서 동작한다.

이 두 설명은 서로 다른 이야기일까?

결론부터 말하면, 모순되는 설명은 아니다. **OSI는 통신 기능을 분류하기 위한 참조 모델이고, 실제 HTTPS 통신은 프로토콜들이 어떻게 함께 동작하는지를 보여주기 때문이다.**

## OSI 계층에 프로토콜을 대응시키는 것의 한계

OSI 7계층은 네트워크 통신에 필요한 기능을 일곱 개의 계층으로 나누어 설명하는 참조 모델이다.

예를 들어 응용 계층은 애플리케이션의 통신 기능을, 전송 계층은 종단 간 데이터 전송을 담당하는 기능을 설명한다.

여기서 주의할 점은 OSI가 실제 인터넷 통신의 구현 구조를 그대로 나타내는 것은 아니라는 것이다.

실제 인터넷에서는 TCP/IP 프로토콜 스택을 중심으로 여러 프로토콜이 함께 동작한다. 또한 프로토콜의 기능이 OSI 계층과 반드시 일대일로 대응하는 것도 아니다.

TLS가 좋은 예다.

TLS는 데이터를 암호화하고 통신 상대를 인증하는 기능을 제공한다. 암호화라는 역할에 주목하면 OSI의 표현 계층(L6)에 비유할 수 있다.

하지만 이 분류만으로는 TLS가 실제 통신에서 어디에 위치하고 어떤 프로토콜과 상호작용하는지 설명하기 어렵다.

따라서 계층을 분류하는 관점과 실제 동작 구조를 살펴보는 관점을 구분해야 한다.

## 실제 HTTPS에서는 TLS가 어떻게 동작할까?

다음과 같이 Spring Boot 서버의 API를 호출하는 상황을 가정해 보자.

```http
GET https://example.com/users
```

일반적인 HTTPS/1.1 통신에서 사용하는 프로토콜의 관계는 다음과 같다.

```text
┌──────────────────────────────┐
│ HTTP                         │
│ 요청과 응답 메시지 정의      │
├──────────────────────────────┤
│ TLS                          │
│ 암호화 및 통신 상대 인증     │
├──────────────────────────────┤
│ TCP                          │
│ 연결 관리, 순서 및 재전송    │
├──────────────────────────────┤
│ IP                           │
│ 주소 지정 및 패킷 전달      │
└──────────────────────────────┘
```

HTTP는 서버에 어떤 리소스를 요청할지 정의한다.

TLS는 HTTP 메시지를 암호화하여 전송 중 제3자가 내용을 쉽게 확인하거나 변조하지 못하도록 보호한다. 또한 인증서를 통해 서버의 신원을 검증하는 데 사용된다.

TCP는 연결을 관리하고 데이터가 순서대로 전달되도록 처리한다.

IP는 목적지 주소를 기준으로 패킷이 네트워크를 통해 전달될 수 있도록 한다.

이 구조에서 TLS는 HTTP와 TCP 사이에 위치한다.

즉, TLS를 OSI 표현 계층에 비유하는 것은 기능을 기준으로 한 설명이고, HTTP와 TCP 사이에서 동작한다고 설명하는 것은 실제 프로토콜 간 관계를 기준으로 한 설명이다.

서로 다른 관점이므로 모순되지 않는다.

## HTTP 요청이 실제로 전송되기까지

프로토콜 간 관계를 이해했다면, 이번에는 요청이 전송되는 순서를 살펴보자.

새로운 HTTPS/1.1 연결을 수립하는 경우 전체 흐름을 단순화하면 다음과 같다.

```text
1. DNS 조회
   example.com에 대응하는 IP 주소 확인
       ↓
2. TCP 연결 수립
   서버와 TCP 연결 설정
       ↓
3. TLS 핸드셰이크
   서버 인증 및 암호화에 필요한 키 설정
       ↓
4. HTTP 요청 전송
   TLS로 보호된 HTTP 메시지 전달
       ↓
5. HTTP 응답 수신
   응답 데이터를 복호화한 뒤 HTTP 메시지 처리
```

여기서 DNS 조회, TCP 연결 수립, TLS 핸드셰이크는 HTTP 요청을 전송하기 위한 준비 과정이다.

다만 매번 이 과정이 모두 반복되는 것은 아니다. 기존 연결을 재사용하면 TCP 연결과 TLS 핸드셰이크를 다시 수행하지 않고 요청을 보낼 수 있다.

또한 위 흐름은 HTTPS/1.1을 기준으로 한 설명이다. HTTP/3는 TCP 대신 QUIC을 사용하므로 전송 구조가 다르다.

이처럼 실제 프로토콜의 동작을 이해하려면 계층 이름뿐 아니라 어떤 프로토콜을 사용하는지, 연결을 어떻게 수립하는지까지 확인해야 한다.

## 정리하며

처음에는 HTTP, TLS, TCP를 OSI의 어느 계층에 배치해야 하는지에 집중했다.

하지만 TLS를 표현 계층이라고 외우는 것만으로는 실제 HTTPS 요청이 어떻게 전달되는지 이해하기 어려웠다.

이번에 정리한 차이는 다음과 같다.

- **OSI 관점:** 네트워크 통신에 필요한 기능을 어떻게 구분하는가?
- **실제 프로토콜 관점:** 각 프로토콜은 무엇을 담당하고 어떻게 상호작용하는가?

OSI는 네트워크 구조를 이해하기 위한 유용한 모델이다. 다만 실제 시스템의 동작을 분석할 때는 참조 모델의 계층 구분과 구현 구조를 혼동하지 않아야 한다.

앞으로는 프로토콜이 몇 계층인지 확인하는 데서 그치지 않고, 실제 요청 흐름에서 어떤 책임을 가지며 다른 프로토콜과 어떻게 연결되는지 살펴보려고 한다.
