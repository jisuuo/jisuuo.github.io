Relay는 공부용으로 만드는 Java/Spring 채팅 서버다(Java 21, Spring Boot 4.1.2, Raw WebSocket). 목적은 기능을 빨리 완성하는 것이 아니라 "문제 발견 → 재현 → 해결책 비교 → 구현 → 테스트·측정 → 기록"을 한 바퀴씩 돌리는 것이다. 과제마다 정의 → 고민 → 설계 → 구현·검증 → 정리의 5단계를 밟는다. 각 단계에서는 AI(Claude)가 질문·힌트·반례를 던지고 내가 먼저 답한다. 코드와 테스트는 내가 구현을 요청한 뒤 AI가 작성했고, 설계 기록(ADR) 같은 문서는 AI가 대화 내용을 바탕으로 작성했다. 아래에서 따옴표로 인용한 내 문장은 진행 기록에 '내 답·내 표현·내 결정'으로 남은 원문이다.

이 글은 네 번째 과제 P1-4 "같은 방 브로드캐스트와 다른 방 격리"를 다룬다. **P1-4는 아직 끝나지 않았다.** 지금은 4단계(구현·검증)에 있고 시나리오 1~7을 실행했다. 시나리오 8(EXP-02 측정)은 아직 실행하지 않았고, 설계 기록 ADR-0009·0010은 Proposed 상태다.

요지는 두 가지다.

- 브로드캐스트(방 멤버 전원에게 보내기)가 정확하려면 "누가 받는가"와 "어떤 순서로 받는가"를 따로 지켜야 했다. 이번에는 복사본, 세션 락, 방 락이라는 서로 다른 장치가 나눠 맡았다.
- 이번 환경에서 동시성 버그는 내가 예상한 모습으로 나타나지 않았다. 방어 없는 구현으로 먼저 깨뜨려 본 덕에 알 수 있었다.

## 불변식 ①: "복사한 순간"이라는 기준에 닿기까지 (정의 단계)

정의 단계의 첫 질문은 불변식, 곧 "누가 받아야 하는가"였다. 내가 처음 적은 문장은 이랬다.

> "같은 방 멤버는 모두 받아야하고, 방 멤버가 아닌 유저들은 받으면 안된다"

AI가 반례를 냈다. 멤버는 계속 바뀐다. 보낸 뒤 `JOIN`한 B, 전송 직전 `LEAVE`한 C는 어떻게 되나? 나는 "SEND 처리 시점의 멤버는 모두 받고, 그 외는 받으면 안 된다"로 고쳤다. 진행 기록은 이 "SEND 처리 시점"을 전체 락 안에서 멤버 목록을 복사하는 순간으로 정리했다. 직전 과제 P1-3에서 방 관리자(RoomRegistry)의 모든 변경을 전체 락 하나로 묶어 두었으므로, 복사도 같은 락 안에서 하면 요청들이 한 줄로 선다. 그 복사가 이 SEND가 "이 한 점에서 일어났다"고 말할 수 있는 지점(선형화 지점)이 된다. 이 기준이면 B는 받지 않고 C는 받는다.

AI의 두 번째 반례는 C가 `LEAVE`가 아니라 끊김을 겪는 경우였다. 복사본에 있어도 보낼 수 없고, 락 안에서 전송하더라도 끊김은 락이 막지 못한다. 나는 "연결이 살아 있는 멤버는 반드시 받고, 멤버가 아니면 받지 않는다"로 고쳤다. AI는 여기서 시점이 빠져 B가 다시 애매해진다고 짚었다. 내 답은 "멤버의 기준은 복사를 하고나서의 있냐로 판단"이었고, 불변식 ①은 이렇게 정해졌다.

> 복사한 순간 방 R의 멤버였던 세션 중 연결이 살아 있는 세션은 반드시 받고, 복사한 순간의 멤버가 아니었던 세션은 받지 않는다.

전송이 실패하면 어떻게 하느냐는 질문에는 "C 다음 사람들에게는 계속 보냅니다"라고 답했다.

이 불변식을 깨는 구현도 문제 문장 ①로 적었다. 내 표현은 "락 없이 원본 목록을 순회하며 전송하면 복사 후 JOIN한 B도 받는다"였고, 다듬은 문장은 이렇다.

> 락 없이 원본 멤버 목록을 순회하며 전송하는 구현에서, 전송 도중 다른 스레드가 `JOIN`·`LEAVE`하면 받는 사람이 하나의 시점으로 정해지지 않는다 → 결과(예상): 전송 시작 뒤 `JOIN`한 B가 받거나, 루프가 `ConcurrentModificationException`으로 끊겨 뒤 순서 멤버가 받지 못한다.

## 같은 세션에 동시 전송이 모이는 이유, 그리고 문제 ④

복사본을 락 밖에서 순회하며 보내면 전체 락을 짧게 잡을 수 있다. 대신 두 문제가 남는다.

**문제 ② 같은 세션 동시 전송.** 세션(WebSocketSession)은 연결 하나를 나타내는 서버 쪽 객체다. 정의 단계 질문 2(동시 접근)에 대한 내 답은 "같은 세션에 두 스레드가 동시에 sendMessage 호출하면 … 섞이거나 덮어씌워질거같다"였다. 확인하지 않은 예상이다. 이때 AI는 섞인다면 내용이 아니라 소켓에 바이트를 쓰는 단계에서 섞이므로 메시지에 `type`이나 ID를 넣어도 막을 수 없다고 보충했다. 이것도 실행 전 설명이다.

고민 단계에서는 이런 동시 전송이 어떻게 생기는지부터 다시 따졌다. 처음 내 반응은 "어떻게 일어나는건가요"였다. 그림으로 정리한 뒤 내 표현은 이렇게 바뀌었다.

> "각 다른 멤버가 한 F에게 보내도, F가 여러방에 있어서 그 방에 있는 F에게 보내도, 자기 자신에게 보내도 session은 같은 객체로 보내기때문에 여러 스레드가 동시에 도착할 수 있어서 섞이거나 덮이는경우가 발생할 수 있다"

원인은 **전송을 받는 사람이 아니라 보낸 사람의 스레드가 한다**는 것이다. A의 `SEND`를 처리하는 스레드도, 다른 방의 `SEND`를 처리하는 스레드도 F의 세션 객체 하나에 쓴다.

**문제 ④ 멤버마다 순서가 다름.** 이 문제는 처음 목록에 없었고 고민 단계에서 나왔다. 보낸 사람 본인에게도 보낼지 정할 때, 내 처음 순서 기준은 "내가 보낸 메시지 시간 기준"이었다. AI는 시계가 사람마다 다르다는 반례를 냈고, 서버 처리 순서 기준과 비교한 뒤 내 결정은 "보낸다, 모두가 같은 순서로 보게 하려고"였다. 이어서 AI가 그 근거를 따라가 지금 설계가 정말 같은 순서를 보장하는지 물었다. 내 답은 "같지 않을 수 있다, T1이 E에서 대기하면 T2가 F에 먼저 도착"이었다. 세션 락은 한 세션 안의 섞임만 막고 멤버 사이의 순서는 지켜 주지 않는다. 순서를 불변식에 넣을지에 대한 내 결정은 "넣는다, 채팅에서 순서가 다르면 대화가 이상해진다"였다.

> 불변식 ②: 같은 방의 멤버들은 메시지를 같은 순서로 받는다.

## 대안 비교와 결정 (고민·설계 단계)

| 문제 | 대안 | 결정 |
|---|---|---|
| ② 같은 세션 동시 전송 | A. 전체 락을 전송에도 사용 / **B. 세션 락 `synchronized (session)` + 전송 메서드 하나** / C. Spring `ConcurrentWebSocketSessionDecorator` | B |
| ④ 멤버마다 순서 다름 | **D. 방 락으로 "복사 + 전송 루프 전체"를 감쌈** / E. 방마다 대기열 + 전담 스레드 | D |

A는 느린 전송 하나가 모든 방의 전송과 `JOIN`·`LEAVE`를 멈춘다. 처음엔 A와 B의 "차이를 정확히 모르겠다"고 했다가, 비유와 타임라인으로 정리한 뒤 "같은 세션끼리만 기다리면 돼서 다른 방은 안 막힌다"며 B를 골랐다. 구현 방식으로 내가 "세션 객체 자체를 열쇠로 쓴다"고 답하자, AI는 모든 호출 위치가 락을 잡아야 하고 한 곳이라도 깜빡하면 조용히 깨진다는 반례를 냈다. 직접 `sendMessage`를 부르는 것은 컴파일러가 막아 주지 않는다. 내 답은 "전송 메서드 하나로 사용 후 락 획득을 여기서 넣는다"였고, 이에 따라 AI가 전송 입구(SessionSender)를 작성했다. 서버 → 클라이언트 전송은 모두 이 메서드를 거친다. C는 기다리지 않고 세션마다 버퍼에 넣은 뒤 반환하며, 시간·버퍼 한도 값을 정해야 하고 느린 소비자 처리까지 함께 들어온다. C와 비교한 뒤 내 선택은 "synchronized + send 하나, 문제 ③은 P1-8로 미뤘으니까"였다.

E는 내 아이디어였다("방에서 메시지를 처리하는건 한 스레드로 … 입구에서 메시지를 대기열로 만들고 하나씩 처리"). 이것을 더 단순한 대안 D와 비교했을 때 내 답은 "대기열은 방마다 스레드가 필요하고, 방마다 락은 느린 F에서 막힌다"였다. AI는 느린 F가 방 R을 막는 것은 둘 다 같고, 차이는 기다리는 쪽이 Tomcat 스레드냐 전담 스레드냐라고 보충했다. ADR-0009의 근거대로 C·E가 더 나은 점은 모두 느린 소비자(문제 ③)에 관한 것이고, 문제 ③은 아직 재현되지 않았다. 문제 ③의 범위에 대한 내 결정은 "P1-8로 넘긴다, 아직 재현된 문제가 없다", D에 대한 내 결정은 "방마다 락, 느린 소비자는 아직 재현 안 돼서"였다.

**방 락 객체 (설계 단계).** 처음 후보는 방 객체(멤버 `Set`)였다. 방이 삭제·재생성되면 어떻게 되느냐는 질문에 내 답은 "다른 열쇠를 잡는다, 삭제된 방과 새 방은 다른 객체"였다(인용의 '열쇠'는 방 락). 그러면 순서 ②가 깨질 수 있다. 기록에 남은 타임라인은 이렇다(처음 타임라인이 틀려 다시 그린 것이고, 재현하지 않은 드문 경우다).

- 옛 방 [F, X, H]에서 X에게 보내는 동안 전송이 느리다.
- 그사이 전원이 퇴장하고 F·H가 재입장한다. 새 방은 새 객체다.
- H의 `SEND`가 다른 방 락을 잡고 기다림 없이 바로 진행한다.
- F는 안녕→하이, H는 하이→안녕 순서로 받는다.

내 첫 판단은 "받아들이고 넘어간다, 드물고 재현 전이니까"였다. AI는 반례를 냈다. 방 객체를 얻으려면 맵 조회(전체 락)가 먼저 필요해 락 순서와 충돌하고, P1-3에서 피했던 재확인·재시도가 다시 들어온다. 그다음 내 답이 "해시값으로 열쇠 배열의 칸을 고른다"였다. 이것이 **락 스트라이핑**이다. 방 이름만으로 칸을 계산하니 맵도 전체 락도 필요 없고, 방이 삭제·재생성돼도 같은 방 락이며, 락을 만들거나 정리할 일도 없다. 서로 다른 방이 같은 칸에 걸리는 경우에 대한 내 답은 "성능 문제, 순서는 지켜지고 쓸데없이 기다리기만 한다"였다. AI가 작성한 브로드캐스터(RoomBroadcaster)는 64칸을 쓰고, 코드 주석에는 64가 임시 값이며 P1-7 측정 후 조정한다고 적혀 있다.

```java
Object lockFor(String roomId) {
    return roomLocks[Math.floorMod(roomId.hashCode(), roomLocks.length)];
}
```

ADR-0009는 락 순서를 항상 **방 락 → 전체 락(멤버 확인·복사 동안만) → 세션 락**으로 정했고, 역방향으로 잡는 경로를 두지 않는다.

## 재현 결과: 예상과 달랐던 두 가지 (구현·검증 단계)

설계 단계에서 적은 실행 전 예상은 이랬다. 시나리오 1은 섞임과 예외 중 무엇이 나올지 모른다, 시나리오 3·4는 방어 없는 구현에서 실패한다, 시나리오 7은 모른다. 아래 시나리오 1·3·4는 AI가 작성한 테스트로 방어 없는 구현에서 먼저 실패하는 것을 확인한 뒤 구현을 바꿔 통과시켰고, 단계마다 5회씩 실행했다.

### 시나리오 1, 문제 ②: 섞임이 아니라 유실

기록용 가짜 세션에는 소켓에 바이트를 쓰는 단계가 없어 섞임을 재현할 수 없으므로 이 테스트는 실제 연결을 쓴다. 서버 쪽 세션 하나에 스레드 8개가 200번씩, 모두 1,600번 동시에 보냈고 메시지는 약 1KB였다. 세션에 직접 `sendMessage`를 부른 방어 없는 구현은 5회 모두 실패했다. 서버 예외가 1,475~1,564번 났고 클라이언트는 59~125개만 받았다. 예외 수와 수신 수를 더하면 언제나 1,600이었다. 형식이 깨진 메시지와 중복은 0개였고, 그동안 서버 세션은 계속 open이었다. 예외는 모두 다음 하나였다.

```
IllegalStateException: The remote endpoint was in state [TEXT_PARTIAL_WRITING] which is an invalid state for called method
```

**예상과 달리 섞임은 관찰되지 않았다.** 이번 환경의 Tomcat은 세션이 "쓰는 중"일 때 들어온 다른 스레드의 쓰기를 예외로 거절했고, 실제 증상은 거절된 메시지의 **유실**이었다. 실행 전 AI가 설명한 바이트 단계의 섞임은 이 조건에서 나오지 않았다. 전송 입구(`synchronized (session)`, 실패하면 `false`)를 적용하자 5회 모두 실패 0, 1,600개 모두 수신이었다.

### 시나리오 3·4, 문제 ①·④: 단계별 결과

시나리오 3·4는 기록용 가짜 세션으로 돌렸다. 이 가짜 세션은 `sendMessage`가 불리는 즉시 받은 내용을 기록하므로, 브로드캐스트가 반환된 직후 "받지 않았다"를 기다림 없이 확정할 수 있다. 시나리오 3은 멤버 4명이 각자 100번 동시에 `SEND`하고 전송마다 0~20µs 무작위 지연을 넣었다. 시나리오 4는 첫 전송에서 멈춘 사이 B가 `JOIN`한 뒤 재개한다. 테스트는 그대로 두고 구현만 바꿨다. 표의 index는 멤버당 400개 수신 목록에서 멤버 0과 다른 멤버의 순서가 처음 달라진 위치다.

| 구현 (각 5회) | 시나리오 4 (불변식 ①) | 시나리오 3 (불변식 ②) |
|---|---|---|
| 방어 없음 (원본 순회, 방 락 없음) | 모두 실패: `ConcurrentModificationException` | 모두 실패: index 14~219에서 순서 갈림 |
| 복사만 (전체 락 안에서 `Set.copyOf`) | 모두 통과 | 모두 실패: index 10~39 |
| 복사 + 방 락 (락 스트라이핑 64칸) | 모두 통과 | 모두 통과 |

예상과 달랐던 두 번째는 시나리오 4다. 처음 내 표현이 예상한 증상(B가 받음)은 나오지 않았고, 다듬은 문제 문장 ①의 두 번째 예상(루프 중단)이 나왔다. B의 `JOIN`이 순회 중인 같은 `HashSet`을 바꾸면서 **루프가 `ConcurrentModificationException`으로 끊겼고**, 그 바람에 C도 받지 못했다.

복사는 받는 사람만 정하고 순서는 지키지 못한다는 고민 단계의 예상은 맞았다. 내 해석은 "복사를 추가하면서 추후에 추가된 B는 안받는걸 확인. 그리고 같은 순서는 방 락 추가로 한 스레드로 처리하게 만들어서 방어되었다"였다. AI는 "한 스레드로"가 아니라 "한 번에 한 스레드씩"이라고 보충했다. 보내는 Tomcat 스레드는 여럿이고 방 락 앞에서 차례로 줄을 선다. 테스트 기록에는 시나리오 3의 통과가 "이 조건에서 앞지르기를 찾지 못했다"는 뜻이며, 순서가 지켜진다는 근거는 방 락 범위에 대한 추론이라고 적혀 있다.

## 전송 실패를 세션 정리 신호로 쓰지 않는다

정의 단계 질문 3(넣고 빼기 짝)에서 AI가 전송 실패 시 브로드캐스트가 그 세션을 정리할지 물었고, 내 답은 "afterConnectionClosed와 heartbeat에 맡긴다"였다. 처음 근거는 "브로드캐스트에서 처리시 병목"이었다. AI는 정리(`removeSession`)가 메모리 연산이라 `sendMessage`(I/O)보다 매우 빠르다는 반례를 냈다. 내가 고친 근거는 "동시 전송 실패일 수도 있어서 살아있는 C를 빼게 된다"였다. ADR-0009는 이것을 이렇게 적었다.

> 전송 실패는 연결 종료일 수도, 동시 전송 같은 다른 이유일 수도 있는 애매한 신호다. 살아 있는 세션을 빼면 이후 메시지를 예외 없이 받지 못해 불변식 ①이 깨진다.

이 규칙의 근거는 앞의 시나리오 1에서 확인됐다. 동시 쓰기로 전송이 계속 실패하는 동안에도 서버 세션은 open이었다. 그때 내 답은 "전송 실패만 보고 세션을 빼지 않는다, 살아있는 세션을 뺄 뻔했다"였다.

시나리오 7은 실패 → 통과 재현이 아니라 **관찰**이다. 기대값을 미리 정하지 않고, 소켓으로 직접 WebSocket 연결 요청(handshake)을 보낸 뒤 close frame(WebSocket 종료 알림) 없이 TCP를 끊었다. 끊는 방식은 TCP의 정상 종료 신호인 FIN(`socket.close`)과 연결을 즉시 끊는 RST(SO_LINGER 0) 두 가지로, 3회 실행 모두 같은 결과였다. 두 경우 모두 서버의 읽기 쪽이 끊김을 알아차렸고 `afterConnectionClosed`가 1006(close frame을 받지 못한 비정상 종료 코드)으로 호출됐다. 그 뒤 전송 입구는 `false`를 돌려줬다. 이번 관찰에서 전송 실패가 끊김을 일으킨 경우는 없었고, "정리는 `afterConnectionClosed` 한 경로에서만 한다"는 규칙과 맞는다. FIN·RST가 아예 도착하지 않는 끊김(네트워크 단절, NAT 타임아웃)은 localhost에서 만들 수 없어 관찰하지 못했고, P1-5 heartbeat에서 다룬다.

## 테스트가 못 잡은 변이 (시나리오 2·5)

시나리오 2(멤버 전원·본인 수신, 다른 방 격리, 비멤버 `SEND`는 `false`, 한 명 실패해도 나머지 수신)와 시나리오 5(같은 이름 같은 방 락, 음수 해시)는 실패 → 통과 순서가 아니다. AI가 구현이 이미 있는 상태에서 테스트를 작성해 처음 실행부터 모두 통과했다. 그래서 테스트가 잘못된 구현을 잡는지, AI가 구현을 일부러 네 가지로 바꿔(변이) 확인하고 원복했다. 세 가지는 잡았지만 **`floorMod` 대신 `Math.abs(hash) % n`을 쓴 변이 3은 잡지 못했다.** 해시가 `Integer.MIN_VALUE`인 문자열을 넣어도 `MIN_VALUE % 64 == 0`이라 64칸에서는 `abs` 방식도 우연히 맞기 때문이다. AI가 처음 쓴 테스트 주석의 "음수 인덱스가 된다"는 설명이 64칸에서는 틀렸고, AI가 주석을 정정했다. `floorMod`는 칸 수를 바꿔도 안전하게 하려는 선택으로 유지했다.

## 서버 메시지와 시나리오 6

서버 → 클라이언트 메시지도 이번에 처음 생겼다. 설계 단계의 내 답은 "ADR-0007처럼 record + sealed interface, 일관성 때문에", "연결 직후 서버가 sessionId를 알려준다"였다. 보낸 사람 본인도 메시지를 돌려받으므로 연결 직후 `CONNECTED`로 자기 sessionId를 알려 주고, 채팅은 `MESSAGE`로 보낸다(ADR-0010, Proposed). 시나리오 6은 실제 클라이언트 3개를 쓴다. 구현 전에는 두 테스트 모두 실패했고("받은 메시지=[]"), AI가 구현을 붙인 뒤 두 번째 테스트가 5회 실패했는데 원인은 테스트 쪽 실수였다. AI가 이를 고친 뒤 5회 모두 통과했다. 다른 방 격리 검사가 버그를 잡는지도 AI가 구현을 일부러 바꿔(모든 방의 멤버를 돌려주게) 실패하는 것을 확인한 뒤 원복했다.

## 남은 것

- **시나리오 8 (EXP-02):** 방 락을 얻는 비용을 비교한다. 방 이름 해시로 락 배열의 칸을 고르는 방식과, 전체 락 안에서 방 객체를 찾고 재확인하는 방식이다. 아직 실행하지 않아 결과가 없다.
- **느린 소비자 (P1-8):** 방 락은 느린 F 앞에서 Tomcat 스레드를 붙잡아 둔다. P1-4에서는 받아들이고, P1-8에서 재현한 뒤 Decorator 같은 후보와 비교한다.
- **ADR-0009·0010은 Proposed:** 5단계(정리)에서 Accepted 여부를 판단한다.

## 직접 해 볼 것

자기 서버에서 `WebSocketSession.sendMessage`를 직접 부르는 곳을 찾아, 그 호출이 여러 스레드에서 동시에 일어날 수 있는지 확인해 보자. 그다음 방어 없는 구현으로 같은 세션 동시 전송 테스트를 먼저 돌려 서버 예외 수, 받은 개수, 형식, 중복을 모두 기록해 보자. 실제 증상은 그 환경에서 돌려 봐야 안다.

## 용어 정리

- 세션(WebSocketSession): 연결 하나를 나타내는 서버 쪽 객체
- 방 관리자(RoomRegistry): 방 ↔ 세션 매핑을 전체 락으로 관리
- 브로드캐스트: 방 멤버 전원에게 보내기
- 브로드캐스터(RoomBroadcaster): 방 락을 잡고 복사본을 순회하며 전송
- 전송 입구(SessionSender): 서버 → 클라이언트 전송의 유일한 메서드
- 멤버 목록 복사본(스냅샷): 전체 락 안에서 복사한 멤버 목록
- 전체 락 / 방 락 / 세션 락
- 락 스트라이핑: 방 이름 해시로 고정 크기(64칸) 락 배열의 칸을 고르는 방식
- 느린 소비자: 받는 속도가 느린 클라이언트(문제 ③)
- 끊김: 연결 종료(afterConnectionClosed)
