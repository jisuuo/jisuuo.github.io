## 1. 들어가며

Spring Boot에서 외부 API를 호출하거나 React에서 서버로 요청을 보내는 일은 익숙하다.

```java
restClient.get()
    .uri("https://api.example.com/users/1")
    .retrieve()
    .body(String.class);
```

개발할 때는 요청을 보내고 응답을 받는 과정에 집중했다. 응답이 느리면 서버 로직이나 DB 쿼리부터 확인하는 경우가 많았다.

그런데 서버의 처리시간은 30ms인데 클라이언트에서는 응답을 받기까지 2초가 걸렸다면 어떨까?

이 경우 서버 코드만 살펴봐서는 원인을 찾지 못할 수 있다.

HTTP 요청은 목적지 서버에 도착하기 전까지 운영체제의 네트워크 스택과 여러 네트워크 장비를 거친다. 따라서 API 장애를 분석하려면 코드 내부뿐 아니라 **요청이 전달되는 전체 흐름을 이해할 필요가 있다.**

이번에는 패킷 스위칭부터 IP, 라우팅, OSPF, BGP, ISP까지 인터넷의 동작 원리를 하나의 API 호출과 연결해 정리해 보았다.

## 2. API 요청은 하나의 데이터 덩어리로 이동하지 않는다

인터넷은 패킷 스위칭(Packet Switching)을 기반으로 동작한다.

패킷 스위칭은 여러 통신이 네트워크 자원을 공유하면서 데이터를 패킷 단위로 전달하는 방식이다.

반면 회선 스위칭(Circuit Switching)은 통신을 위해 일정한 네트워크 자원을 미리 확보하는 방식이다.

```text
[회선 스위칭]

사용자 A ─── 전용으로 할당된 자원 ─── 목적지

[패킷 스위칭]

사용자 A ─┐
사용자 B ─┼── 공유 네트워크 링크 ─── 목적지
사용자 C ─┘
```

인터넷에서는 여러 사용자가 동시에 API 호출, 파일 다운로드, 동영상 스트리밍 등을 수행한다.

패킷 스위칭은 이러한 통신들이 네트워크 자원을 효율적으로 공유하도록 한다. 다만 동시에 많은 패킷이 몰리면 문제가 발생할 수 있다.

```text
네트워크 트래픽 증가
        ↓
장비의 출력 링크에 패킷 집중
        ↓
Queue에서 대기
        ↓
Queuing Delay 증가
        ↓
버퍼 부족 시 Packet Loss 발생 가능
        ↓
TCP 재전송 및 응답 지연 가능
```

여기서 처음 연결된 개념은 **패킷 손실이 반드시 API 오류로 드러나는 것은 아니라는 점**이다.

TCP는 손실된 데이터를 재전송해 복구를 시도한다. 따라서 네트워크에서 패킷 손실이 발생하더라도 애플리케이션에서는 단순히 응답이 느려진 것처럼 보일 수 있다.

### TCP와 IP의 책임

HTTP/1.1을 TCP 위에서 사용하는 경우를 기준으로 보면 다음과 같다.

```text
HTTP
  └─ 어떤 리소스를 요청할 것인가?

TCP
  └─ 신뢰성 있는 순서화된 바이트 스트림 제공

IP
  └─ 목적지 주소를 기반으로 패킷 전달

Network Interface
  └─ 실제 네트워크를 통한 송수신
```

IP는 패킷의 전달 성공이나 순서를 보장하지 않는다. TCP는 재전송과 순서 제어 등을 통해 애플리케이션에 신뢰성 있는 바이트 스트림을 제공한다.

이 과정은 계층별 책임 분리이자 추상화의 예시이기도 하다.

애플리케이션 개발자는 일반적인 HTTP 호출에서 패킷 손실과 재전송을 직접 구현하지 않아도 된다. 하지만 **TCP가 하위 계층의 문제를 처리하는 동안 응답시간이 증가할 수 있다는 사실**은 알고 있어야 한다.

## 3. 네트워크에서 발생하는 지연은 어떻게 구분할까?

패킷이 네트워크 장비를 거칠 때 발생하는 지연은 크게 네 가지로 구분할 수 있다.

| 종류 | 의미 |
|---|---|
| Processing Delay | 장비가 패킷을 검사하고 처리하는 시간 |
| Queuing Delay | 다른 패킷 때문에 대기하는 시간 |
| Transmission Delay | 패킷의 비트를 링크에 내보내는 시간 |
| Propagation Delay | 신호가 물리적인 거리를 이동하는 시간 |

여기서 전송 지연과 전파 지연을 구분할 필요가 있다.

전송 지연은 패킷 크기와 링크의 전송 속도에 영향을 받는다.

$$
\text{Transmission Delay} = \frac{\text{Packet Size (bits)}}{\text{Bandwidth (bps)}}
$$

전파 지연은 신호가 이동해야 하는 거리와 전파 속도에 영향을 받는다.

즉, **대역폭이 충분히 높더라도 목적지까지의 지연시간이 반드시 짧아지는 것은 아니다.**

### Store-and-Forward와 Cut-Through

네트워크 장비가 데이터를 다음 장비로 전달하는 방식도 지연에 영향을 줄 수 있다.

- **Store-and-Forward:** 전체 프레임이나 패킷을 받은 후 다음 링크로 전송을 시작한다.
- **Cut-Through:** 전달에 필요한 정보를 확인한 후 전체 데이터를 받기 전에 전송을 시작할 수 있다.

Cut-Through는 주로 이더넷 스위칭에서 설명하는 방식이다. 모든 라우터가 Cut-Through로 동작하는 것은 아니다.

이러한 전달 방식과 지연의 관계를 이해하면, API 응답시간을 단순히 서버 로직 실행시간으로만 생각하지 않게 된다.

## 4. 운영체제는 목적지 IP까지 어떻게 패킷을 보낼까?

다음과 같이 회사 내부 API를 호출한다고 가정해 보자.

```http
GET http://10.50.2.170:8080/users
```

여기서 IP 주소는 목적지를 식별하는 데 사용하고, 포트 번호는 목적지 호스트의 전송 계층 통신 접점을 식별하는 데 사용한다.

하지만 IP 주소를 알고 있다고 해서 패킷이 자동으로 목적지까지 도착하는 것은 아니다.

운영체제는 **라우팅 테이블(Routing Table)**을 참고해 어느 인터페이스 또는 다음 홉으로 패킷을 전달할지 결정한다.

```text
React / Spring Boot
        │
        ▼
운영체제 네트워크 스택
        │
        │ 목적지 IP 확인
        ▼
라우팅 테이블 조회
        │
        ▼
출력 네트워크 인터페이스 선택
        │
        ▼
라우터를 통해 패킷 전달
```

### VPN을 연결해야 사내 API가 호출되는 이유

예를 들어 Mac의 라우팅 테이블이 다음과 같다고 가정하자.

```text
10.50.2.0/24  → utun4 (VPN)
0.0.0.0/0     → en0   (Wi-Fi)
```

`10.50.2.170`으로 보내는 패킷은 더 구체적인 `10.50.2.0/24` 경로와 일치하므로 VPN 인터페이스를 선택한다.

반면 다른 목적지 IP는 기본 경로로 전달될 수 있다.

여기서 `/24`는 IPv4 주소 32비트 중 앞의 24비트를 네트워크 접두부로 사용한다는 뜻이다.

```text
10.50.2.0/24

포함: 10.50.2.170
제외: 10.50.3.10
```

운영체제가 목적지와 가장 길게 일치하는 접두부의 경로를 우선 선택하는 원리를 **Longest Prefix Match**라고 한다.

또한 VPN의 가상 인터페이스인 `utun4`와 실제 Wi-Fi 인터페이스인 `en0`은 역할이 다르다.

VPN을 이용해 패킷을 전달하더라도 터널 통신 자체는 물리적인 Wi-Fi 연결을 사용할 수 있다.

macOS에서는 다음 명령어로 목적지에 선택된 경로를 확인할 수 있다.

```bash
route -n get 10.50.2.170
```

하지만 라우팅 테이블에 VPN 경로가 존재한다는 것은 **패킷을 보낼 방향이 결정되었다는 의미이지, API 호출이 성공한다는 보장은 아니다.** 방화벽, 서버의 포트 리스닝 상태 등은 별도로 확인해야 한다.

## 5. 라우터는 목적지까지의 경로를 어떻게 학습할까?

운영체제가 라우팅 테이블을 확인하는 것은 이해했다.

그렇다면 라우터의 라우팅 정보는 어떻게 만들어질까?

관리자가 정적으로 경로를 설정할 수도 있지만, 라우터들이 서로 경로 정보를 교환하는 동적 라우팅 방식도 있다.

여기서 OSPF와 BGP가 등장한다.

### OSPF — AS 내부 경로 계산

OSPF(Open Shortest Path First)는 링크 상태 기반 라우팅 프로토콜이다.

라우터들은 링크 상태 정보를 공유하고, 이를 바탕으로 네트워크의 연결 구조를 파악한다.

```text
Router A
   │
   ├── Router B ── Cost 20 ── 목적지
   │
   └── Router C ── Cost 10 ── 목적지
```

OSPF는 링크의 Cost를 활용해 다익스트라(Dijkstra) 알고리즘으로 최소 비용 경로를 계산한다.

여기서 중요한 것은 **Cost가 실제 API 응답시간을 뜻하지 않는다는 점**이다.

Cost가 낮은 경로를 선택하더라도 네트워크 혼잡이나 패킷 손실 때문에 API 응답은 느릴 수 있다.

OSPF의 주요 패킷은 다음과 같다.

| 패킷 | 역할 |
|---|---|
| Hello | 이웃 라우터 발견 및 관계 유지 |
| DBD | 링크 상태 정보 요약 교환 |
| LSR | 필요한 링크 상태 정보 요청 |
| LSU | LSA를 담아 링크 상태 정보 전달 |
| LSAck | LSA 수신 확인 |

이 과정을 통해 링크 상태 데이터베이스(LSDB)를 구축하고 최단 경로 계산에 필요한 정보를 확보한다.

네트워크 링크에 장애가 발생하면 변경된 상태를 반영해 경로를 다시 계산할 수 있다. 경로 전환 중에는 일시적인 패킷 손실이나 지연이 발생할 수 있다.

### BGP — AS 사이의 경로 정보 교환

인터넷은 하나의 회사가 운영하는 네트워크가 아니다.

여러 조직이 각자의 정책에 따라 네트워크를 운영하며 서로 연결하고 있다.

이처럼 하나의 라우팅 정책 아래 운영되는 네트워크 집합을 **AS(Autonomous System)**라고 한다.

BGP(Border Gateway Protocol)는 이러한 AS 내부 및 AS 사이에서 경로 정보를 교환하는 데 사용하며, 특히 AS 사이의 라우팅에 핵심적인 역할을 한다.

```text
회사 네트워크
      │
      ▼
AS 100
      │
      ▼
AS 200
      │
      ▼
외부 API 서버
```

BGP에서는 AS_PATH와 LOCAL_PREF 등의 속성이 경로 선택에 영향을 준다.

- **AS_PATH:** 경로 광고가 거쳐 온 AS의 정보
- **LOCAL_PREF:** AS 내부에서 어떤 경로를 우선 사용할지 나타내는 선호도

BGP는 AS_PATH가 짧다고 무조건 해당 경로를 선택하지 않는다. 네트워크 운영 정책이 중요한 판단 기준이다.

따라서 외부 API 응답이 느려졌다고 해서 반드시 애플리케이션에 문제가 있다고 볼 수 없으며, 외부 네트워크 경로의 변화도 가능한 원인에 포함된다.

## 6. ISP와 IXP는 인터넷을 어떻게 연결할까?

ISP(Internet Service Provider)는 인터넷 연결을 제공하는 사업자다.

서로 다른 ISP가 트래픽을 교환할 수 있도록 연결하는 지점이 IXP(Internet Exchange Point)다.

사업자 간 연결 방식에는 대표적으로 두 가지가 있다.

- **Peering:** 서로 다른 네트워크가 직접 트래픽을 교환하는 관계
- **Transit:** 다른 사업자에게 비용을 지불하고 더 넓은 인터넷 네트워크로 접근하는 서비스

이 연결 관계에 따라 ISP를 Tier 1·2·3으로 구분하기도 한다.

| 분류 | 특징 |
|---|---|
| Tier 1 | 다른 사업자에게 Transit을 구매하지 않고 전 세계 인터넷에 도달 |
| Tier 2 | Peering과 Transit을 함께 사용 |
| Tier 3 | 주로 Transit을 구매하여 인터넷 접속 서비스 제공 |

이 분류는 성능 등급이 아니다.

Tier 1이 반드시 더 빠르다는 의미도 아니며, 실제 인터넷 경로가 항상 Tier 3 → Tier 2 → Tier 1 순서로 구성되는 것도 아니다.

이 개념을 통해 이해한 것은 **인터넷이 하나의 거대한 네트워크가 아니라, 여러 사업자의 네트워크가 서로 연결된 구조**라는 점이다.

## 7. 실제 API 장애가 발생하면 어떻게 접근할까?

처음의 상황으로 돌아가 보자.

```text
React → Network → Nginx → Spring Boot

클라이언트 전체 응답시간: 2,000ms
Spring Boot 처리시간: 30ms
```

이때 Spring Boot의 처리시간만 보고 나머지 1,970ms가 모두 네트워크 지연이라고 판단해서는 안 된다.

먼저 각 측정 구간을 정의하고, 같은 요청에서 어느 구간에 시간이 소비됐는지 확인해야 한다.

### 1단계. 연결 및 응답 시간 측정

```bash
curl -s -o /dev/null \
  -w 'dns: %{time_namelookup}\nconnect: %{time_connect}\ntls: %{time_appconnect}\nttfb: %{time_starttransfer}\ntotal: %{time_total}\n' \
  https://api.example.com/users
```

각 시간은 요청 시작 시점부터 누적된 값이다. 따라서 필요하면 인접한 값을 빼서 구간별 시간을 계산해야 한다.

예를 들어 TCP 연결은 빨랐는데 첫 응답까지 오래 걸렸다면 연결 이후 구간을 추가로 조사한다.

### 2단계. 목적지 경로 확인

```bash
route -n get 10.50.2.170
```

VPN을 통해 사설망에 접근하는 환경이라면 목적지에 선택된 인터페이스가 의도한 경로인지 확인한다.

### 3단계. TCP 포트 연결 확인

```bash
nc -vz -G 3 10.50.2.170 8080
```

연결이 실패한다면 라우팅, 방화벽, 서버 리스닝 상태 등을 조사한다.

### 4단계. HTTP 응답과 서버 처리시간 비교

HTTP 응답이 도착했다면 상태 코드와 서버 로그를 확인한다.

특히 Nginx를 사용한다면 `$request_time`, `$upstream_response_time` 등을 기록하여 프록시와 업스트림 처리 구간을 비교할 수 있다.

다만 하나의 도구만으로 모든 장애 원인을 확인할 수는 없다. 측정 결과를 서로 비교하면서 원인을 좁혀야 한다.

### 장애 분석의 기본 순서

```text
① 현상 확인
   API 응답에 2초 소요
          ↓
② 측정
   서버 처리시간은 30ms
          ↓
③ 범위 좁히기
   연결 설정 / 네트워크 / 프록시
          ↓
④ 가설 수립
   경로 문제? 연결 대기? 패킷 손실?
          ↓
⑤ 추가 측정으로 검증
          ↓
⑥ 원인 파악 및 조치
```

핵심은 **오류 증상만으로 원인을 단정하지 않는 것**이다.

## 8. 정리하며

이번 학습 전에는 API 요청이 네트워크를 통해 서버에 도착한다는 정도로만 이해하고 있었다.

하지만 패킷 스위칭부터 라우팅, OSPF, BGP, ISP의 관계를 공부하면서 하나의 API 요청이 여러 계층과 네트워크를 거쳐 처리된다는 점을 구체적으로 이해하게 되었다.

특히 다음 세 가지가 기억에 남는다.

첫째, **패킷이 손실되어도 TCP의 재전송 때문에 애플리케이션에서는 단순한 응답 지연으로 보일 수 있다.**

둘째, **라우팅 테이블에서 목적지 경로가 선택되었다는 사실과 실제 서버에 연결할 수 있다는 사실은 다르다.**

셋째, **라우팅 프로토콜이 선택한 경로가 반드시 실제 API 응답시간이 가장 빠른 경로는 아니다.**

앞으로 API 장애를 만났을 때는 서버 코드를 먼저 의심하기보다, 요청이 어떤 구간을 지나고 어디에서 지연되는지부터 확인하려고 한다.

인터넷의 동작 원리를 공부하는 목적은 프로토콜 이름을 외우는 것이 아니라, **실제 문제를 만났을 때 확인할 범위를 스스로 좁혀갈 수 있는 기준을 만드는 것**이라고 생각한다.

## 매일 복습할 핵심

```text
API 호출
   ↓
HTTP: 요청과 응답의 의미
   ↓
TCP: 신뢰성 있는 바이트 스트림
   ↓
IP: 목적지 주소 기반 전달
   ↓
라우팅 테이블: 다음 홉/인터페이스 선택
   ↓
OSPF: AS 내부 최소 Cost 경로 계산
   ↓
BGP: AS 간 경로 정보 및 정책
   ↓
ISP/IXP: 인터넷 네트워크 간 연결
   ↓
목적지 서버
```

> 위 그림은 개념을 연결한 학습용 흐름이다. 매 API 요청이 OSPF나 BGP를 순서대로 호출한다는 뜻은 아니다. 라우팅 프로토콜은 경로 정보를 학습·갱신하고 실제 패킷은 라우팅 결과를 기반으로 전달된다.

**장애가 발생하면 스스로 확인할 질문**

1. 요청이 목적지 서버에 도착하기는 했는가?
2. DNS·TCP 연결·TLS·첫 응답까지 각각 얼마나 걸렸는가?
3. 운영체제가 선택한 라우팅 경로는 올바른가?
4. 서버 처리시간과 클라이언트 전체 응답시간의 차이는 어디에서 발생했는가?
5. 네트워크 장애라는 가설을 뒷받침할 측정 결과가 있는가?

### 후속 심화 학습 주제

이번 글에서는 개념의 관계와 장애 분석의 출발점을 중심으로 정리했다.

추후에는 다음 주제를 별도 글로 심화해 볼 예정이다.

- **네트워크 성능:** RTT, MTU, MSS, TCP 재전송, 혼잡 제어, Head-of-Line Blocking
- **운영체제:** Socket, File Descriptor, 커널 네트워크 버퍼, NIC, 인터럽트
- **자료구조와 알고리즘:** 다익스트라, 우선순위 큐, 라우팅 테이블의 최장 접두부 일치
- **라우팅:** OSPF 수렴 과정, BGP 정책, Route Flap, 비대칭 라우팅
- **관찰 가능성:** Nginx 계측, TCP 패킷 분석, Distributed Tracing, 요청 구간별 지연 분석
