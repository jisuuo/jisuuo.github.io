Relay는 Java 21, Spring Boot 4.1.2로 만드는 학습용 채팅 서버다. 목적은 기능 완성이 아니라 "문제 발견 → 재현 → 해결책 비교 → 구현 → 테스트·측정 → 기록"을 반복하는 것이다. AI(Claude)가 질문과 힌트를 주면 내가 먼저 답했고, 코드와 테스트는 내가 구현을 요청한 뒤 AI가 작성했다.

이 글은 첫 과제(P1-1, WebSocket 연결과 종료)에서 내린 두 결정을 다룬다.

1. WebSocket 위에 필요한 것을 직접 만들지, STOMP에 맡길지
2. 연결이 예고 없이 끊겼을 때 서버가 어떻게 알아챌지

실행한 것은 로컬 테스트뿐이다. 설계 결정 문서(ADR)의 내용은 실행해 보지 않은 판단이고, 직접 확인하지 않은 일반 지식에는 `(일반 지식)`을 붙였다.

## 왜 WebSocket인가

HTTP만으로 채팅이 어려운 이유를 묻자 나는 'http 요청/응답 방식은 양방형이 아니기에 다른 서버에서 나에게 올 메시지가 있는지 알려주지못한다. 그래서 webscoket을 사용해서 진행.'이라고 답했다. 핵심은 서버가 클라이언트에게 먼저 보낼 수 없다는 점으로 바로잡혔다. 클라이언트가 주기적으로 묻는 polling은 주기를 짧게 하면 빈 응답이 늘고, 길게 하면 지연이 커진다(일반 지식).

WebSocket은 HTTP 요청으로 핸드셰이크(handshake)를 하고, 서버가 `101 Switching Protocols`로 응답하면 같은 TCP 연결에서 frame이라는 단위로 데이터를 주고받는다. 정상 종료 때는 close frame을 주고받는다(일반 지식).

## 결정 1: STOMP 대신 Raw WebSocket

ADR-0004의 배경에 따르면 WebSocket은 연결 유지와 frame 전달만 제공한다. 채팅방을 만들려면 그 위에 네 가지가 필요하다.

1. 메시지 형식
2. 방 → 세션 매핑
3. 같은 방 세션들에 대한 브로드캐스트
4. 끊긴 세션을 매핑에서 정리

STOMP는 WebSocket을 대체하지 않고 그 위에 얹는 메시징 규칙이다(일반 지식). STOMP를 쓰면 메시지 브로커(Message Broker), 즉 구독자에게 메시지를 나눠 주는 주체가 생긴다. 그중 Simple Broker는 서버 메모리 안에서 동작하고, 외부 브로커는 RabbitMQ 같은 별도 프로그램이다(일반 지식).

ADR-0004가 비교한 대안은 셋이다.

- **A. Raw WebSocket(`WebSocketHandler`)**: 네 가지의 동작과 실패 지점이 모두 코드에 드러나 문제를 직접 재현할 수 있다. 대신 메시지 규칙과, 메시지를 어느 세션에 보낼지 정하는 라우팅을 직접 만들고, 표준 클라이언트 라이브러리가 없으며, 직접 짠 코드의 버그도 떠안는다.
- **B. STOMP + Simple Broker**: 표준 프로토콜과 클라이언트 라이브러리가 있고, 네 가지 대부분을 프레임워크가 처리한다. 대신 방 관리와 브로드캐스트 내부가 가려지고, 다중 서버 문제는 A와 똑같이 남는다.
- **C. STOMP + 외부 브로커(RabbitMQ 등)**: 서버 간 전달까지 해결하는 확장 경로다. 하지만 P1은 단일 서버라 해결할 문제가 아직 없고, 외부 인프라가 추가된다.

나는 'Raw WebSocket으로 시작. 직접 만들어봐야 문제를 알 수 있음'이라고 답했고, ADR-0004의 결정도 A다. ADR은 근거를 두 가지로 적었다. 직접 만들어야 동시 수정, 끊긴 세션, 동시 전송, 느린 소비자 같은 문제를 실패하는 테스트로 재현할 수 있다. 그리고 B의 확장 이점은 C로 가야 얻을 수 있는데, C는 아직 재현된 문제가 없다.

이해를 확인하는 질문에서 나는 STOMP를 쓰지 않으면 네 가지를 Raw WebSocket이 만들어야 하니 그 비용을 줄이려고 STOMP를 쓴다고 이해하고 있었다. AI의 설명을 듣고 두 가지를 바로잡았다. 네 가지를 만드는 주체는 개발자이고, STOMP의 이점에는 비용 절감 말고도 표준과 확장 경로가 있다.

### 언제 다시 검토할까

이 질문에 처음에는 '잘 모르겠습니다.'라고 답했다. 그래서 서버 2대 예시를 따져 봤다. 두 사용자 A와 B가 서로 다른 서버에 연결되어 있을 때 B가 A의 메시지를 받을 수 있는가. 내 답은 '못 받는다. 서버 2에는 A의 세션이 없어서.'였다. 이어서 'smtop의 위치는 서버들 중간에 있나요'라고 물었고, 한동안 STOMP와 외부 broker의 역할을 잘못 이해했다가 대화 중에 바로잡았다. 이 과정을 거쳐 정한 기준이 '서버가 여러 대가 되어 서버 간 메시지 전달'이다.

ADR-0004의 재검토 조건도 같다. 서버가 여러 대가 되어 서버 간 메시지 전달 문제가 재현되면 두 길을 다시 비교한다. 하나는 Raw WebSocket을 유지하고 Redis Pub/Sub·Kafka 등으로 서버끼리 전달하는 길이고, 다른 하나는 STOMP + 외부 브로커로 바꾸는 길이다.

## 결정 2: 비정상 단절은 ping/pong으로

연결 때 할 일을 처음에는 '연결되면 세션을 확인?'이라고 답했고, 대화 중 세션 저장소(SessionRegistry)에 등록하는 것으로 구체화했다. 종료 때 할 일은 '세션을 저장소에서 제거해야 함. 안 하면 끊긴 세션이 계속 남음'이었다.

제거는 `afterConnectionClosed`가 호출되어야 일어난다. ADR-0005의 구분에 따르면 정상 종료에서는 클라이언트가 close frame을 보내므로 서버가 바로 안다. 비정상 단절(네트워크 단절, 프로세스 강제 종료 등)에서는 close frame이 오지 않는다.

서버가 비정상 단절을 어떻게 아느냐는 질문에 나는 '연결에 메시지를 보낼때 할 수 있습니다.'라고 답했다. ADR-0005는 이 방법의 한계를 두 가지로 적었다.

1. `send`는 데이터를 OS의 송신 버퍼에 넣으면 성공으로 끝난다. 그래서 상대 호스트가 사라져도 TCP가 다시 보내기(재전송)를 포기할 때까지 수 분 이상 실패가 드러나지 않을 수 있다(일반 지식).
2. 방이 조용해 보낼 메시지가 없으면 끊긴 세션이 계속 남는다.

조용한 방에서는 어떻게 되느냐는 질문에 내 답은 '끊긴 세션은 계속 남습니다. ping 테스트나 헬스체크로 확인해야할 거 같습니다.'였다. 보낼 메시지가 없어도 연결을 주기적으로 확인하는 heartbeat가 필요하다는 뜻이다.

ADR-0005는 heartbeat 방식 세 가지를 비교했다.

- **A. TCP keepalive**: 애플리케이션 코드가 필요 없다. 하지만 OS 기본값 기준 2시간 유휴 뒤에야 시작하고(설정에 따라 다름, 일반 지식), 감지 시점을 애플리케이션이 통제하기 어렵다.
- **B. WebSocket ping/pong frame**: 브라우저 같은 클라이언트가 pong을 자동으로 응답하므로 클라이언트 코드가 필요 없다. 대신 ping 전송, pong 추적, 타임아웃 종료는 서버가 직접 만들어야 한다. 브라우저 JS는 ping을 보내거나 pong을 확인할 수 없어서 클라이언트 쪽 감지는 해결되지 않는다(브라우저 동작은 일반 지식).
- **C. 애플리케이션 메시지(`{"type":"PING"}`)**: 형식이 자유롭고 양방향 감지가 된다. 대신 클라이언트도 응답 로직을 만들어야 하고, 메시지 모델에 제어용 타입이 섞인다.

주기에 대해 나는 '5초로 짧게 잡으면 부하가 올 수 있고, 5분이면 이미 닫힌 세션에 충분히 연결을 시도할 수 있다?'라고 답했다. ADR-0005가 정리한 트레이드오프는 이렇다. 주기가 짧으면 비용이 늘고, 잠깐 신호가 약해진 연결을 끊긴 것으로 잘못 볼 수 있다. 길면 끊긴 세션이 오래 남고, 정상 연결도 끊길 수 있다. 중간의 프록시·로드밸런서가 한동안 데이터가 오가지 않는 연결을 끊는 유휴 타임아웃 때문이다(예: Nginx 기본 60초, 일반 지식).

최종 선택은 B였고, 이유는 '클라이언트 코드 없이 자동 응답이라서'였다. 클라이언트 쪽 감지 한계에 대해 ADR-0005는 P1의 목표가 서버 쪽 세션 정리라서 지금은 문제가 되지 않는다고 본다. 주기·타임아웃 값은 ADR에서 정하지 않았고, 설계·구현 단계에서 정해 테스트로 확인한다. 시작 기준은 "주기 수십 초, 타임아웃은 주기의 2~3배"다.

## 구현과 확인 (실행한 것)

AI가 작성한 연결·종료 통합 테스트(WebSocketConnectionTest)는 서버를 실제 포트로 띄우고 `/ws`에 연결한다. 그다음 세션 저장소 크기가 1이 되는지, 정상 종료 뒤 0이 되는지 확인한다. 서버의 연결·종료 처리는 테스트 쪽 호출과 다른 스레드에서 비동기로 실행되므로, 테스트는 최대 5초 동안 기대값을 기다린다.

핸들러와 `/ws` 엔드포인트가 없는 상태에서 `./gradlew test --tests 'com.relay.websocket.WebSocketConnectionTest'`를 실행하자 두 테스트 모두 실패했다.

```
java.util.concurrent.ExecutionException: jakarta.websocket.DeploymentException:
The HTTP response from the server [404] did not permit the HTTP upgrade to WebSocket
```

`/ws`가 없어서 핸드셰이크에 101 대신 404가 돌아온 것이다. 그다음 AI가 핸들러(`ChatWebSocketHandler`)와 설정(`WebSocketConfig`)을 구현했다. 아래는 핸들러의 두 메서드만 옮긴 발췌이고, 주석은 원문 그대로다.

```java
// 이유: 서버가 세션 객체를 받는 유일한 시점이다. 여기서 보관하지 않으면 이후 이 사용자에게 보낼 방법이 없다.
@Override
public void afterConnectionEstablished(WebSocketSession session) {
	registry.add(session);
}

// 이유: 끊긴 세션이 남으면 메모리 누수·접속자 수 왜곡·이후 전송 실패가 생긴다.
// 주의: close frame이 오지 않는 비정상 단절에서는 이 메서드가 제때 호출되지 않을 수 있다 → P1-5 heartbeat (ADR-0005).
@Override
public void afterConnectionClosed(WebSocketSession session, CloseStatus status) {
	registry.remove(session);
}
```

`WebSocketConfig`는 `@EnableWebSocket`으로 이 핸들러를 `/ws`에 등록한다. 구현 뒤 `./gradlew test --rerun-tasks` 전체 실행에서 4개 테스트가 모두 통과했다(macOS 로컬 한 대). 이 결과가 보여 주는 것은 정상 종료에서 등록과 제거가 핸들러를 거쳐 일어난다는 데까지다.

## 한계와 다음 과제

- heartbeat는 구현하지 않았고, 비정상 단절은 테스트하지 않았다. 다음 과제(P1-5)에서 다룬다.
- 서버 2대 구성, STOMP, 외부 브로커는 실행해 보지 않았다. 이 글의 비교는 설계 판단이다.

## 독자가 해볼 것

직접 만들지 프레임워크에 맡길지 정하기 전에 두 줄을 적어 보자. **무엇이 숨겨지는가**, 그리고 **언제 다시 검토할지(재검토 조건)**. 이 글에서는 네 가지 기능(메시지 형식·방 → 세션 매핑·브로드캐스트·끊긴 세션 정리)과 '서버 간 메시지 전달 문제의 재현'이었다.

## 용어 정리

- 세션(WebSocketSession): 서버가 연결 하나를 표현하는 객체.
- 세션 저장소(SessionRegistry): 연결된 세션을 보관하는 곳.
- 등록 / 제거: 세션 저장소에 세션을 넣기 / 빼기.
- 정상 종료: close frame을 주고받는 종료.
- 비정상 단절: close frame 없이 연결이 끊기는 것.
- 핸드셰이크(handshake): WebSocket 연결을 시작하는 HTTP 요청·응답 과정.
- frame: WebSocket 연결에서 주고받는 단위. 이 글에는 close frame과 ping/pong frame이 나온다.
- heartbeat: 보낼 메시지가 없어도 주기적으로 연결을 확인하는 것.
- ping/pong: heartbeat에 쓰는 WebSocket 제어 frame.
- Raw WebSocket: STOMP 없이 WebSocketHandler로 직접 다루는 방식.
- 메시지 브로커(Message Broker): 구독자에게 메시지를 나눠 주는 주체.
- 연결·종료 통합 테스트(WebSocketConnectionTest): 실제 클라이언트로 연결하고 정상 종료하며 세션 저장소를 확인하는 테스트.
