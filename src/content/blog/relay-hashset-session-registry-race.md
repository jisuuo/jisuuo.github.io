학습용 Java/Spring 채팅 서버 Relay를 만들면서, 연결된 세션(`WebSocketSession`)을 보관하는 세션 저장소(`SessionRegistry`)를 평범한 `HashSet`으로 두고 동시 등록 테스트(`SessionRegistryTest`)를 돌렸다. 측정 범위는 로컬 macOS 한 대(Java 21, Spring Boot 4.1.2)에서 구현별로 10회씩 실행한 것이 전부다. 그러니 다른 환경에서도 같은 결과가 나온다고 일반화할 수는 없다. 이 범위에서 `HashSet` 세션 저장소는 동시 등록 테스트 10회에서 모두 실패했고, 같은 테스트로 `ConcurrentHashMap.newKeySet()`은 10회 모두 통과했다. `HashSet` 쪽 테스트 결과에는 `size()` 단언 실패(`AssertionFailedError`)만 있었고 다른 예외는 기록되지 않았다. 등록했는데 세션 저장소에서 빠져 있는 것, 즉 유실이 예외 없이 생긴 것이다.

이 글은 그 실패를 일부러 만들어 낸 과정이다. 핵심은 수치보다 테스트 설계에 있다. **이 테스트가 안전하지 않은 구현에서 먼저 실패하는지 확인하지 않으면, 두 구현을 구분하는 테스트인지 알 수 없다.**

진행 방식도 먼저 밝혀 둔다. AI(Claude)가 질문과 힌트를 주고 내가 먼저 답하는 식으로 진행했다. 코드와 테스트는 내가 구현을 요청한 뒤 AI가 작성했다. 이때 주석에 왜 이렇게 했는지 이유를 남기고, 실패 후 다시 구현하면 파일 아래에 이력을 정리해 달라고 요청했다. 아래 따옴표 인용은 그 대화에서 내가 한 말을 오탈자까지 그대로 옮긴 것이다.

## 세션 저장소는 왜 필요하고, 왜 여러 스레드가 동시에 쓰나

WebSocket 연결이 맺어지면 서버는 `afterConnectionEstablished`에서 세션 객체를 딱 한 번 받는다. 처음에 나는 연결 시 할 일을 '연결되면 세션을 확인?' 정도로 생각했다. 하지만 세션은 이때 한 번만 받으므로, 어딘가에 보관해 두지 않으면 이후 그 사용자에게 메시지를 보낼 방법이 없다. 그래서 세션 저장소를 두고 연결 시 등록하고 종료 시 제거한다. 종료 시 제거하지 않으면 끊긴 세션이 남아 메모리 누수, 접속자 수 왜곡, 전송 실패로 이어진다.

`Set`을 쓰는 이유는 코드 주석에 적혀 있다. 필요한 연산은 등록·제거·전체 반복·개수이고, 같은 세션이 두 번 들어갈 일이 없으며 순서도 필요 없다.

문제는 호출하는 쪽이다. 일반적으로 Tomcat은 연결 이벤트를 스레드 풀의 여러 스레드로 처리하므로, `afterConnectionEstablished`가 동시에 호출될 수 있다. 이 호출들이 같은 세션 저장소 객체를 쓴다면 여러 스레드가 같은 `Set`에 동시에 쓰게 된다. 동시 등록 테스트는 서버를 띄우지 않고, 세션 저장소 하나에 100개 스레드가 동시에 등록하는 부분만 만든다.

## 경쟁 조건: 한 줄짜리 add도 여러 단계다

나는 이 지점에서 막혔다. '정확하게 이 부분이 이해가 안됩니다. 스레드가 여러개면 왜 저장하는데 문제가 생기는지와 경쟁 조건이 생기는지'라고 물었다.

가장 단순한 예는 `count = count + 1`이다. 일반적으로 알려진 바로는 한 줄이지만 실제로는 **읽기 → 계산 → 쓰기** 세 단계다. `count`가 0일 때 스레드 1과 스레드 2가 둘 다 0을 읽고, 각자 1을 계산해 쓰면 결과는 2가 아니라 1이다. 한 번의 증가가 덮어써진다. 이렇게 실행 순서에 따라 결과가 달라지는 상황을 경쟁 조건(race condition)이라고 한다. 나는 이 예시를 보고 '스레드1이 쓰기까지 끝낸 뒤 스레드 2가 읽으면 2'라고 답했다. 단계가 겹치지 않으면 맞고, 겹치면 틀린다.

`HashSet.add`도 같다. 알려진 바로는 `HashSet`은 내부 `HashMap`의 key로 원소를 넣고, `hashCode`로 버킷 위치를 계산한다. 기본 capacity 16, load factor 0.75라서 원소가 12개를 넘으면 2배 크기 배열을 만들어 원소를 옮기는 resize가 일어난다. 그러니 `add` 한 번도 count 예시처럼 '버킷에 원소를 잇기 → size 늘리기 → (필요하면) resize'라는 여러 단계로 나뉜다. 이 단계 사이에 다른 스레드가 끼어들 수 있다는 점이 count 예시와 같다. 코드의 변경 이력 주석에는 "다른 스레드가 중간 상태를 보고 작업하면 결과가 덮어써지거나 resize 중 기존 배열에 들어간 원소가 버려진다"는 추정이 적혀 있다.

다만 이번 유실이 resize·원소 잇기·size 증가 중 어디에서 몇 건 생겼는지는 확인하지 않았다. 위 설명은 일반적으로 알려진 동작과 주석에 근거한 추정이다.

세션 저장소에서 빠진 사용자 B에게는 무슨 일이 생길까. 내 답은 이랬다. '연결은 되어서 전송은 할 수 있지만 메시지가 전달되지 않습니다.' 세션 저장소 코드 주석에 적힌 대로, 보관하지 않은 세션에는 이후 메시지를 보낼 방법이 없기 때문이다.

## 해결 원리와 세 구현 비교

해결의 열쇠는 원자성(atomicity)이다. 여러 단계를 다른 스레드가 끼어들 수 없는 하나의 단위로 만드는 것이다. 일반적으로 방법은 크게 두 가지다.

- **락(lock)**: 한 스레드가 작업하는 동안 다른 스레드는 기다린다.
- **CAS(Compare-And-Swap)**: "내가 읽은 값이 아직 그대로면 바꾸고, 아니면 실패"를 한 번에 수행한다. 이 동작을 묻는 질문에 나는 '스레드1이 먼저 바꿔서 값이 달라 실패, 포기하면 1'이라고 답했다.

후보는 세 가지였다.

| 후보 | 동작 방식(일반 지식) | 판단 |
|---|---|---|
| ① `Collections.synchronizedSet(new HashSet<>())` | 모든 연산에 락 하나 | 동시에 등록하는 스레드가 그 락을 차례로 기다림 |
| ② `ConcurrentHashMap.newKeySet()` | 빈 버킷은 CAS로 삽입, 원소가 있으면 그 버킷에만 락 | 선택 |
| ③ `CopyOnWriteArraySet` | 쓰기마다 배열 전체 복사 | 연결·종료가 잦은 세션 저장소에 맞지 않음 |

처음에 나는 '접속자가 수천이기에 동시에 버킷을 건드리지만 원자연산을 통해 무조건 락이 해제되어야 가능하도록 해아한다. 그래서 2번입니다.'라고 답했다. 그러자 AI가 핵심은 **락을 버킷 단위로 잘게 나누는 것**이라고 바로잡아 주었다. 알려진 동작으로는 서로 다른 버킷을 건드리는 스레드끼리는 기다리지 않는다. ('수천'은 내가 가정한 규모일 뿐 목표치나 측정치가 아니다.)

①과 ③은 실행하지도 측정하지도 않았다. 이 둘을 뺀 근거는 동작 방식에 대한 일반 지식이지 성능 측정이 아니다.

## 테스트 설계: 왜 순차 테스트로는 안 되나

처음 떠올린 테스트는 '100개의 세션이 저장되고 현재 있는 concureentHashmap 세션의 갯수를 세면 됮 않을까요'였다. 그런데 이 테스트는 `HashSet`에서도 통과할 것이다. 이유를 묻자 나는 '단순 저장이기 때문입니다. 스레드가 동작하지 않고, 세션이름을 명시하지 않았기 때문입니다.'라고 답했다. AI는 뒤의 '세션이름' 부분은 관계없다고 바로잡아 주었다. 남는 이유는 스레드 하나가 순서대로 등록하면 단계가 겹칠 일이 없어 경쟁 조건이 생기지 않는다는 것이다. 두 구현 모두에서 통과하는 테스트는 둘을 구분하지 못한다. (순차 버전을 실제로 돌려 본 것은 아니고, 논리로 판단했다.)

그래서 나온 답이 '출발 신호를 주고 동시에 시작하게 한다'였다. 아래는 AI가 작성한 동시 등록 테스트의 코드 주석에 적힌 설계 의도다. 이 중 어느 것도 따로 실험해 확인하지는 않았다.

- **규모: 100 스레드 × 스레드당 100 세션.** 주석에는 "경쟁 조건은 확률적으로 발생한다. 스레드 수와 스레드당 작업량을 키워 단계가 겹칠 기회를 늘린다."라고 적혀 있다. 이어서 "원소가 많아야 HashSet 내부의 resize가 여러 번 일어나 유실이 생길 구간이 많아진다"고도 적혀 있다.
- **Mockito로 만든 가짜 세션(mock)을 출발 전에 미리 생성.** 주석에는 "세션(mock) 생성은 add보다 훨씬 느리다. 출발 전에 미리 만들어 두어야 출발 후에는 스레드들이 add만 하며 실제로 겹친다."라고 적혀 있다. 이 시간은 재지 않았다.
- **출발 신호(`CountDownLatch`).** 주석에는 "스레드는 생성·시작에 시간이 걸린다. 출발 신호 없이 시작하면 앞 스레드가 끝난 뒤 다음 스레드가 출발해 사실상 순차 실행이 되므로, 모두 출발선에서 기다리게 한 뒤 동시에 출발시킨다."라고 적혀 있다.
- **완료 대기용 `CountDownLatch`(`done`)와 `finally`의 `countDown`.** 출발 신호와 같은 클래스를 완료 대기에도 쓴다. 모든 스레드가 끝나기 전에 개수를 세어 잘못된 실패가 나지 않게 하고, `add` 중 예외가 나도 메인 스레드가 무한히 기다리지 않게 하기 위해서다.

아래는 테스트 메서드에서 스레드 출발·완료 대기·검증 부분만 옮긴 발췌다(주석 제외).

```java
CountDownLatch startSignal = new CountDownLatch(1);
CountDownLatch done = new CountDownLatch(THREADS);
ExecutorService executor = Executors.newFixedThreadPool(THREADS);
for (List<WebSocketSession> sessions : sessionsByThread) {
	executor.submit(() -> {
		try {
			startSignal.await();
			sessions.forEach(registry::add);
		}
		catch (InterruptedException e) {
			Thread.currentThread().interrupt();
		}
		finally {
			done.countDown();
		}
	});
}

startSignal.countDown();
assertThat(done.await(10, TimeUnit.SECONDS)).isTrue();
executor.shutdown();

assertThat(registry.size()).isEqualTo(THREADS * SESSIONS_PER_THREAD);
```

## 실제 결과

`./gradlew test --tests 'com.relay.websocket.SessionRegistryTest' --rerun-tasks`를 `HashSet`으로 10회 연속, `ConcurrentHashMap.newKeySet()`으로 같은 명령을 10회 실행했다. 기대값은 10000이다.

| 세션 저장소 구현 | 결과 | `size()` 값 |
|---|---|---|
| `HashSet` | 10회 모두 실패 | 1~4회차는 보지 않음. 5~10회차: 7988, 6611, 8301, 8460, 8468, 8546 |
| `ConcurrentHashMap.newKeySet()` | 10회 모두 통과 | 10000 |

테스트 코드는 그대로 두고 구현만 바꿨을 때 실패가 통과로 바뀌었으므로, 이 테스트는 적어도 이 환경에서 두 구현을 구분한다.

이 테스트는 서버를 띄우지 않는 단위 테스트라 서버 로그는 보지 않았다. 이후 전체 `./gradlew test`(4개 테스트)도 통과했다.

회고에서 내가 남긴 말은 이것이다. '예외를 주지 않기 때문에 잃어버린 유실에 관해 알수가 없습니다.'

## 한계와 다음 과제

- 하드웨어 사양(코어 수 등)은 기록하지 않았다.
- 유실 원인별 비중은 확인하지 않았다.
- 출발 신호 없는 버전과 규모를 줄인 버전은 실행하지 않았다. 그래서 위 설계 의도 중 출발 신호와 규모의 효과는 가설로 남아 있다.

## 직접 해볼 것

자기 코드에서 여러 스레드가 함께 쓰는 컬렉션을 하나 찾아보자. 싱글톤 빈의 필드가 대표적이다. 그 컬렉션에 출발 신호로 동시에 출발시키는 테스트를 붙이고, **먼저 안전하지 않은 구현에서 실패하는지 확인**한 뒤에 안전한 구현으로 바꿔 본다.

## 용어 정리

- 세션(WebSocketSession): 서버가 연결 하나를 표현하는 객체.
- 세션 저장소(SessionRegistry): 연결된 세션을 보관하는 곳.
- 등록: 세션 저장소에 세션을 넣는 것.
- 유실: 등록했는데 세션 저장소에서 빠져 있는 것.
- 경쟁 조건(race condition): 여러 스레드의 실행 순서에 따라 결과가 달라지는 상황.
- 원자성(atomicity): 여러 단계를 다른 스레드가 끼어들 수 없는 하나의 단위로 수행하는 성질.
- 락(lock): 한 스레드가 작업하는 동안 다른 스레드를 기다리게 하는 장치.
- CAS(Compare-And-Swap): 읽은 값이 그대로일 때만 바꾸고, 아니면 실패하는 원자적 연산.
- resize: 원소가 기준을 넘으면 더 큰 배열을 만들어 원소를 옮기는 과정.
- 출발 신호(CountDownLatch): 모든 스레드를 동시에 출발시키는 장치.
- 동시 등록 테스트(SessionRegistryTest): 여러 스레드가 동시에 등록해도 유실이 없는지 검증하는 테스트.
