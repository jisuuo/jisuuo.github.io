keepup은 Spring Boot와 MySQL로 만드는 학습 프로젝트이고, 이 글은 그 운영기의 셋째 날 기록이다. 요청 하나가 톰캣에 도착해서 내 코드에 닿기까지 어떤 줄에서 기다릴 수 있는지 기본값을 확인하고, 한도를 아주 작게 줄인 서버로 직접 줄을 세워 봤다.

**요약**
1. 이 환경의 톰캣 기본값은 스레드 최대 200개, 동시 연결 최대 8192개, OS 대기열 길이로 넘기는 값(`accept-count`) 100, 스레드 풀 작업 큐 2147483647칸이었다.
2. Spring 설명문은 accept-count를 "처리 스레드가 모두 사용 중일 때"의 대기 줄이라고 하지만, 소스에서 이 값은 OS의 연결 대기열 길이로 넘어간다(소스로 확인). 스레드가 다 바쁠 때 요청이 서는 곳은 스레드 풀의 작업 큐다. 작업 큐는 사실상 무한이지만, 그 길이는 연결 수 한도(`max-connections`)에 묶인다고 추론했다.
3. 한도를 줄인 실험(1회)에서 OS 대기열에 섰던 것으로 보이는 요청은 연결이 즉시 끝났고, 그 대기열마저 찬 것으로 보이는 요청은 거절되지 않고 연결 자체가 2.2~6.1초 늦어졌다.

## 1. 오늘의 목표

실제로 요청이 들어올 때부터 톰캣이 스레드를 배정하고 컨트롤러까지 가는 길이 궁금했다.

DAY 002에서 "톰캣의 대기 줄 3종(`threads.max`, `max-connections`, `accept-count`)이 각각 어떤 줄인지"를 다음에 볼 것으로 남겼고, 오늘은 그 기본값을 숫자로 확인하는 데서 시작했다. 로드맵 체크리스트로는 Q2("서버 안에서 누가 처리하지?")와 Q5(자료구조, 여기서는 큐)에 해당한다.

## 2. 따라간 요청

요청 하나가 톰캣에 도착해서 내 필터에 닿기까지 서는 줄을 순서대로 정리했다. 이 그림은 측정이 아니라 이 프로젝트가 쓰는 소스(Spring Boot 4.1.1의 `TomcatServerProperties`, Tomcat 11.0.24의 `NioEndpoint`·`Acceptor`·`TaskQueue`)를 읽고 그린 것이다.

먼저 용어 몇 개:
- **backlog**: TCP 연결 수립(3-way handshake)은 끝났지만 서버 프로그램이 아직 `accept()`로 받아 가지 않은 연결이 서는 OS 커널의 대기열. 톰캣의 `accept-count`가 이 길이로 OS에 넘어간다(일반적으로 알려진 TCP 동작이고, macOS가 실제로 이 길이를 그대로 쓰는지는 확인하지 않음).
- **Acceptor**: backlog에서 연결을 꺼내(`accept()`) 톰캣으로 들여오는 톰캣 스레드.
- **Poller**: 들여온 연결 여러 개를 지켜보다가 요청 데이터가 도착한 연결을 찾아 스레드 풀에 일을 넘기는 톰캣 스레드.
- **keep-alive**: 응답을 보낸 뒤에도 다음 요청을 위해 TCP 연결을 끊지 않고 유지하는 것.

```
클라이언트
  │ TCP 3-way handshake
  ▼
[OS 커널 대기열 (backlog)]   ← accept-count (100)
  │ Acceptor가 accept()로 꺼냄 — 단, 연결 수가 max-connections 미만일 때만
  ▼
[톰캣이 관리하는 연결들]     ← max-connections (8192)
  │ Poller가 요청 데이터가 들어온 연결을 찾아 작업을 만듦
  ▼
[스레드 풀] 쉬는 스레드가 있으면 그 스레드가 처리
           → 없으면 200개까지 새로 만듦 → 200개가 다 바쁘면 ↓
  ▼
[스레드 풀 작업 큐]          ← max-queue-capacity (2147483647)
  ▼
스레드가 꺼내서 실행 → 필터 → 컨트롤러
```

단순화한 그림이다. 실제로는 쉬는 스레드에게 넘길 때도 작업 큐를 거치고, 큐를 건너뛰는 건 새 스레드를 만들 때뿐이다(4절).

내가 정리한 흐름:

> 클라이언트 TCP 연결 3-way를 지나고서 OS 커널에서 먼저 대기열(accept-count)에 넣고 톰캣이 가져간다. 단 max-connections가 남아 있을 때. 그리고 스레드 풀로 넘어가는데, 스레드 풀이 다 작동 중이면 작업 큐(max-queue-capacity)에서 기다린다. 그리고 스레드가 꺼내서 필터를 지나 컨트롤러로 간다.

보탤 점: 톰캣이 연결을 가져간 직후가 아니라, **그 연결로 요청 데이터가 도착했을 때** 스레드 풀로 일을 넘긴다. 그래서 요청 없이 유지되는 keep-alive 연결은 연결 수는 차지해도 스레드는 잡지 않는다(일반적으로 알려진 NIO 커넥터, 즉 톰캣의 논블로킹 연결 처리 방식의 구조이고, 이번에 Poller 소스로 확인하거나 재지는 않았다).

## 3. 측정값

### A. 기본값

설정 파일은 바꾸지 않고, 실행 옵션으로만 Actuator(Spring Boot의 운영용 엔드포인트 모음)의 `configprops`(Spring이 바인딩한 설정값)와 `metrics`(실행 중인 톰캣이 보고하는 값)를 열어서 확인했다.

| 항목 | Spring 설정값 (`configprops`) | 톰캣이 보고하는 값 (`metrics`) |
|---|---|---|
| `threads.max` | 200 | `tomcat.threads.config.max` = 200 |
| `threads.min-spare` | 10 | `tomcat.threads.current` = 10 (현재 떠 있는 스레드 수, 설정값 아님) |
| `max-connections` | 8192 | `tomcat.connections.config.max` = 8192 |
| `accept-count` | 100 | 해당 metric 없음 |
| `threads.max-queue-capacity` | 2147483647 | 해당 metric 없음 |

`threads.max`와 `max-connections`는 두 출처의 값이 일치했다. `min-spare`는 비교할 설정 metric이 없고, 측정 시점에 떠 있던 스레드 수가 같은 값(10)이었다.

Boot 4에서는 톰캣 설정이 `ServerProperties`가 아니라 `TomcatServerProperties`(`@ConfigurationProperties("server.tomcat")`)라는 별도 빈에 들어 있다. 그래서 처음에 `server` prefix 빈을 뒤졌을 때는 값이 하나도 안 나왔다.

### B. 축소판 실험 (11:18, 1회)

- 설정: `threads.max=2`, `threads.min-spare=2`, `max-connections=4`, `accept-count=2` (실행 옵션)
- 3초 sleep하는 실험용 `/debug/slow` 엔드포인트(실험 후 삭제)에 curl 10개를 0.1초 간격으로 연달아 보냄
- 환경: macOS 로컬
- connect는 curl의 TCP 연결 수립 시간, total은 응답을 다 받을 때까지의 시간이다. 보낸 시각은 첫 요청을 0초로 둔 값이고, 0.1초 간격으로 보낸 것에서 계산했다(직접 재지 않음).

| 요청 | 보낸 시각 | connect | total | 해석 (시간 값과 설정으로 추론) |
|---|---|---|---|---|
| 1, 2 | 약 0.0 / 0.1s | 0.0003s | 3.0s | 스레드가 바로 처리 |
| 3, 4 | 약 0.2 / 0.3s | 0.0003s / 0.001s | 5.8s | 작업 큐에서 약 3초 대기 |
| 5, 6 | 약 0.4 / 0.5s | 0.0003s | 8.6s | accept-count 줄 (연결은 즉시 됨) |
| 7, 8 | 약 0.6 / 0.7s | 6.1s | 14.4s | 연결 자체가 지연 |
| 9, 10 | 약 0.8 / 0.9s | 2.2s | 11.2s | 연결 자체가 지연 |

- 10개 모두 200, 실패 없음.
- 서버 로그의 스레드는 `exec-1`, `exec-2` 둘뿐이고, 로그 시각으로 3초마다 두 줄씩(04.6·04.7초 → 07.6·07.7초 → … → 16.6·16.7초) 처리가 끝났다.
- 요청이 어느 줄에 서 있었는지는 직접 보지 않았다. 해석 열은 시간 값과 한도 설정을 맞춰 본 추론이고, macOS에서 `accept-count=2`가 그대로 2칸으로 동작한다고 가정했다(미확인).
- 추론한 시간순 연쇄: 약 3.0초에 1, 2번이 끝나 연결 2개가 반납됨 → Acceptor가 backlog에 있던 5, 6번을 꺼냄 → backlog 2칸이 빔 → 그때 재시도한 9, 10번이 연결됨. 약 6.0초에 3, 4번이 끝나면서 같은 일이 한 번 더 일어나 7, 8번이 연결됨(5절 가설).

## 4. 배운 것: 한 층 아래

- **작업 큐가 21억 칸이어도 큐 길이는 `max-connections`에 묶인다(추론).** 큐에서 기다리는 요청도 응답을 받아야 하니 연결을 잡고 있다. HTTP/1.1에서 연결 하나가 한 번에 요청 하나를 처리한다고 보면, 계산상 큐에 동시에 쌓일 수 있는 건 많아야 8192 − 200개쯤이다(측정하지 않은 계산값). 다만 그만큼 쌓였을 때 대기 시간까지 괜찮은지는 재지 않았다.
- **"연결됐다"는 "서버가 내 요청을 받았다"가 아니다.** 5, 6번은 accept-count 줄에 있었다고 추론되는데도 connect가 1, 2번과 같은 0.0003초였다. backlog는 handshake가 끝난 연결이 서는 줄이라, 클라이언트 쪽에서는 이미 연결된 것으로 보인다.
- **설명문과 코드가 달랐다.** Spring의 accept-count 설명은 "when all possible request processing threads are in use"(처리 스레드가 모두 사용 중일 때)인데, 실제로 이 값은 서버 소켓의 backlog로 OS에 넘어간다(`serverSock.bind(addr, getAcceptCount())`, 소스로 확인). 스레드가 다 바쁠 때 요청이 서는 곳은 작업 큐였다.
- **자료구조(큐):** 톰캣 스레드 풀의 작업 큐는 `TaskQueue`(`LinkedBlockingQueue`를 상속)다. `offer()`는 쉬는 스레드가 없고 스레드 수가 최대보다 적을 때만 `false`를 돌려줘서 새 스레드를 먼저 만들게 한다. 쉬는 스레드가 있으면 큐에 넣고, 쉬던 스레드가 꺼내 간다(소스로 확인).
  - 큐는 작업을 만드는 쪽(Poller)과 처리하는 쪽(워커 스레드)의 속도 차이를 완충하려고 쓴다(내 이해, 따로 확인하지 않음).
  - `ThreadPoolExecutor`에 무한 큐를 붙이면, 기본 스레드(corePoolSize)가 모두 바쁠 때 새 작업은 큐에서 기다리고 스레드는 corePoolSize보다 늘어나지 않는다(Tomcat 11.0.24에 들어 있는 `ThreadPoolExecutor` Javadoc의 'Unbounded queues' 문단 기준). TaskQueue는 스레드를 최대치까지 먼저 늘린 뒤 큐에 쌓으려고 쓴다.
  - TaskQueue도 크기 2147483647의 사실상 무한 큐다. 큐 자료구조는 그대로 쓰고, 핵심은 넣는 규칙인 `offer()`를 바꾼 것이다. `poll()`·`take()`도 재정의하는데, 소스 주석에 따르면 필요할 때 현재 스레드를 멈춰 메모리 누수를 막기 위한 것이다. 스레드 풀이 거절한 작업을 큐에 강제로 넣는 `force()`도 추가돼 있다(소스로 확인).
  - TaskQueue는 스프링이 아니라 톰캣 클래스이고, 스프링 부트는 톰캣을 띄우면서 `server.tomcat.*` 값을 넘겨준다(`TomcatServerProperties` 바인딩까지 확인했고, 톰캣에 적용하는 코드는 읽지 않음).

내 추측과 실제:
- 추측 1 "스레드 200개가 다 바쁠 때 201번째 요청은 accept-count 줄에 선다" → 틀림. 작업 큐에 선다. 그 연결은 이미 `accept()`된 상태다.
- 추측 2 "줄이 꽉 차면 거절, 프록시가 있다면 먼저 오류를 반환" → 이 실험에서는 거절 대신 연결 지연이 일어났다. 연결 수 한도에 닿으면 Acceptor가 `accept()`를 멈추고, 새 연결은 OS 대기열(accept-count)에 남는다. 그 줄까지 찬 7~10번은 거절되지 않고 연결이 늦어졌다. 기본값에서 작업 큐보다 연결 수 한도가 먼저 닿는다는 건 추론이고, 이번 실험은 큐가 2칸 이하인 설정이라 따로 검증하지 않았다. 프록시는 아직 없어서 확인하지 못했다.

오늘 가장 기억에 남는 것: 요청이 스레드에 배정되고 실제 컨트롤러까지 가는 흐름.

## 5. 막힌 것 / 다음에 볼 것

- **9, 10번이 먼저 보낸 7, 8번보다 먼저 연결된 이유 (가설, 미확인)**
  - 가설: accept-count까지 찬 상태에서 macOS가 연결 요청 패킷(SYN)을 거절 응답(RST) 없이 버렸고, 클라이언트가 각자 SYN을 다시 보냈다. 자리가 난 순간에 재시도 SYN이 도착한 쪽이 먼저 들어갔다.
  - 근거: 9번은 0.8초 + connect 2.2초 = 약 3.0초에 연결됐고, 1, 2번이 끝난 시점(약 3.0초)과 맞는다. 재시도 간격이 같다면 7번의 같은 차례 재시도는 약 2.8초로, 자리가 나기 직전이다. 7번은 0.6초 + 6.1초 = 약 6.7초에 연결됐는데, 3, 4번이 끝나 자리가 난 약 6.0초 직후다. 보낸 시각은 계산값이라 이 맞춤도 근사다.
  - 확인 방법: `tcpdump`로 SYN 버림·재전송과 재시도 간격이 일정한지를 직접 본다.
- 큐에 수천 개가 쌓였을 때 뒤쪽 요청이 얼마나 기다리는지, 클라이언트 타임아웃이 먼저 나는지는 재지 않았다.
- 스레드가 `min-spare`에서 `max`까지 늘어나는 순서(스레드 먼저, 그다음 큐)를 측정으로는 확인하지 않았다.
- HTTP/2나 비동기 처리에서 큐 길이가 어떻게 묶이는지는 확인하지 않았다.
- OS마다 backlog가 찼을 때의 반응이 다를 수 있다. Linux에서는 다시 재야 한다.
- DAY 002에서 남긴 "요청마다 스레드가 바뀌는 이유", "필터 앞 약 50ms"(DAY 002의 13:43 실행), "HikariCP `connectionTimeout` 30초 실험"은 오늘 보지 않았다.

결론은 이 환경(macOS, Boot 4.1.1, Tomcat 11.0.24)에서 한 번 재서 "이렇게 관찰됐다"까지다.
