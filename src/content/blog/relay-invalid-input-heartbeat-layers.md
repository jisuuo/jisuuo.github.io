Relay는 Java 21·Spring Boot 4.1.2·Raw WebSocket으로 만드는 학습용 채팅 서버다(저장소: https://github.com/jisuuo/relay). 과제마다 정의 → 고민 → 설계 → 구현·검증 → 정리 다섯 단계를 밟는다. AI(Claude)가 질문·힌트·반례를 던지면 내가 먼저 답하고, 코드·테스트·문서는 내가 요청한 뒤 AI가 작성했다. 이 글은 시리즈 다섯 번째 글이고, 다섯 단계를 모두 마친 과제 P1-5 '잘못된 입력과 비정상 종료 처리'의 기록이다.

P1-5에서 다룬 문제는 세 가지다.

- 클라이언트가 아무 신호 없이 사라지면, 서버에 그 세션(유령 세션)이 계속 남는다.
- 깨진 JSON 한 번에 연결이 1011로 끊긴다.
- 방 멤버가 아닌 세션이 그 방에 `SEND`해도 아무 응답이 없다.

세 문제를 지나며 얻은 결론은 **증상이 보이는 곳만 보고 원인 계층을 짐작하면 안 된다**는 것이다. 문제마다 모양이 달랐다. 유령 세션은 아래 계층(네트워크·OS)에서 생기고 우리 코드에서 보인다. 깨진 JSON은 우리 코드에서 생기지만 결과(1011로 닫기)는 Spring이 정한다. 비멤버 `SEND`는 우리 코드에서 생기고 어디에도 보이지 않는다. P1-4까지와 달리 이번에는 코드만 봐서는 이해가 안 됐다.

## 고치기 전에 먼저 본 것: 실험 1~5

설명만 쌓이자 이해가 끊겨서, 내가 먼저 결과를 예상하고 실행해서 본 뒤 보완하는 방식으로 바꿨다. 서버 코드는 바꾸지 않고 로컬 한 대에서 수동으로 했다. 임시 Node 스크립트와 `kill -STOP`, `lsof`, `netstat`, `jstack`, `javap`를 썼고 스크립트는 저장소에 남기지 않았다.

### 실험 1·2: 유령 세션은 71초 동안 그대로였다

클라이언트 C가 방 A에 `JOIN`한 뒤 `kill -STOP`으로 C 프로세스를 멈췄다. FIN(정상 종료 신호)도 RST(강제 종료 신호)도 가지 않는다. 단, C 쪽 OS는 살아 있어 TCP 응답(ACK)은 한다. 진짜 유령의 절반만 흉내 낸 셈이다.

- 예상: “세션이 사라지지 않으면 호출되지 않을 거 같습니다”
- 결과: 71초 동안 `afterConnectionClosed`가 불리지 않았다. `lsof`로 보니 양쪽 TCP 모두 `ESTABLISHED`(OS가 연결이 살아 있다고 보는 상태)였다.

결과는 맞았지만 이유는 순서가 거꾸로였다. 세션이 남아서 호출이 안 된 게 아니라, 서버 읽기 쪽에 FIN·RST·Close 프레임 중 아무것도 오지 않아서 호출이 안 됐고, 그 결과로 세션이 남았다.

이어서 B가 같은 방에 `SEND`를 1개 보냈다(실험 2). 예상은 “성공합니다. 세션이 남아있는 기준이니깐 발송은 성공입니다.”였고, 실제로 서버 로그에 전송 실패가 없었다. `netstat`에서는 서버→C 소켓 `Send-Q 0`, C 소켓 `Recv-Q 84`였다. 메시지는 C의 OS 수신 버퍼에 도착해 쌓여 있었고, 멈춘 앱이 읽지 않았을 뿐이다. `sendMessage`는 OS에 넘기면 돌아온다. 상대 앱이 읽었는지는 모른다.

> **문제 문장 1.** FIN·RST 없이 클라이언트가 사라지고 그 세션에 보낼 데이터가 없으면 불변식 ③(끊긴 세션은 매핑에 없다)이 깨진다 → 71초 동안 `afterConnectionClosed`가 호출되지 않고, 세션은 매핑에, TCP는 `ESTABLISHED`로 남는다.

### 실험 3: 버퍼가 차면 방이 멈춘다

멈춘 C가 있는 방 A에서 B가 1KB `SEND` 20,000개를 몰아 보냈다. 예상은 “OS 버퍼가 꽉 차서 못 받을 거 같습니다.”였다.

1차 실행은 실패한 실험이었다. 내용을 `'x'` 반복으로 채웠더니 연결이 `permessage-deflate`(압축)를 협상해 메시지가 거의 0으로 줄었고, 2초 안에 20,000개가 모두 B에게 도착했다. 실험 조건을 잘못 잡은 것이다. 무작위 내용으로 다시 돌렸다.

2차 실행에서 B는 812개를 받고 약 20초 멈췄다. 같은 방 D는 5초 동안 아무것도 못 받았고, 다른 방 Z의 E는 1ms에 받았다. `jstack`(스레드 상태 덤프)을 떠 보니, B의 `SEND`를 처리하는 스레드가 방 락과 C의 세션 락을 쥔 채 Tomcat `sendMessageBlock`(소켓에 다 쓸 때까지 기다리는 곳)에서 대기 중이었다. D의 `SEND` 스레드는 같은 방 락을 얻지 못해 `BLOCKED`였다. 약 20초 뒤 C 전송이 `Write timeout`으로 실패하자 Tomcat이 C 연결을 닫았고(1006, 비정상 종료), `afterConnectionClosed`가 불린 뒤에야 B가 나머지를 받았다.

예상과 달랐던 점이 두 가지 있었다.

- 방 락은 버퍼 때문에 새로 걸리는 게 아니었다. 순서 보장(P1-4) 때문에 원래 전송 내내 쥐고 있고, 버퍼가 차면 쥐는 시간이 길어질 뿐이다.
- 4편(P1-4)에서 '전송 실패가 종료로 이어지는 경우는 관찰되지 않음'이라고 적었는데, 쓰기 시간 초과라는 다른 경로로 전송이 종료로 이어졌다. 다만 보낼 데이터가 없으면(실험 1) 이 경로도 생기지 않는다.

방이 멈추는 문제는 방 락을 쥔 채 보내는 설계가 함께 원인이라 P1-8(느린 소비자)로 넘겼다. P1-5에서는 대화가 없을 때 유령이 남는 쪽만 다룬다.

### 실험 4·5: 깨진 JSON은 1011, 비멤버 SEND는 침묵

B가 `{"type":"SEND", "roomId":`처럼 잘린 JSON을 보냈다. B는 즉시 `code=1011 reason=""`로 닫혔고, 이어 보낸 정상 `SEND`는 예외 없이 버려졌다. 서버에는 `ExceptionWebSocketHandlerDecorator : Closing session due to exception` ERROR 로그만 남았다. 1011은 RFC 6455에서 '서버 내부 오류'다. 클라이언트 잘못을 서버 잘못이라고 알려 주는 셈이다. 그래서 이 문제에서 깨지는 것을 둘로 적었다.

> **문제 문장 2.** 깨진 JSON 한 번이 들어오면 연결 유지와 정확한 오류 정보가 둘 다 깨진다.

실험 5에서는 방 A 멤버인 B가 방 X에 `SEND`했다. 예상은 “X 멤버에게 아무런 메시지가 오지 않지만, 정상 send 성공 처리는 될 거 같습니다.”였다. 결과는 1초 동안 아무도 아무것도 받지 않았고, B 연결은 유지됐으며, 서버 WARN/ERROR 로그는 0줄이었다. B는 X에 보내졌다고 믿을 수 있다.

> **문제 문장 3.** 방 멤버가 아닌 세션이 그 방에 `SEND`하면 정확한 오류 정보가 깨진다(연결은 유지).

## 계층 지도: 생기는 곳과 보이는 곳

세 문제를 서버 계층에 놓아 보았다.

```
⑤ 우리 코드      핸들러 · 방 관리자 · 브로드캐스터 · 전송 입구
④ Spring WS     afterConnectionClosed를 '언제' 부를지 결정, 예외를 잡아 1011로 닫음
③ Tomcat        프레임 읽기·쓰기, 쓰기 시간 초과
② OS            송신·수신 버퍼, TCP(ACK·FIN·RST)
① 네트워크        FIN·RST가 사라지는 곳 (localhost로는 재현 불가)
```

| 문제 | 생기는 곳 | 결과를 정하는 곳 | 보이는 곳 |
|---|---|---|---|
| 유령 세션 | ①·② 신호가 사라짐 | ④ 신호가 없으니 닫힘을 부르지 않음 | ⑤ 매핑에 세션이 남음 |
| 깨진 JSON | ⑤ 파서 예외를 안 잡음 | ④ 예외를 잡아 1011로 닫음 | 클라이언트 (1011, 빈 reason) |
| 비멤버 `SEND` | ⑤ `false`만 돌려주고 끝 | ⑤ | 없음 (응답도 로그도 없음) |

세 줄의 모양이 모두 다르다. 아래에서 생겨 위에서 보이는 것은 유령 세션뿐이고, 깨진 JSON은 우리 코드의 빈틈을 Spring이 처리하며 증상이 정해졌고, 비멤버 `SEND`는 증상 자체가 없었다. 깨진 JSON 경로는 `javap`로 Spring jar를 열어 확인했다. 우리 핸들러를 감싼 `ExceptionWebSocketHandlerDecorator`가 예외를 잡아 ERROR 로그를 남기고 `close(SERVER_ERROR)`를 부른다.

## 결정 1: 오류 응답은 어디서, 어떤 모양으로

오류를 어디서 보낼지 묻자 내 첫 답은 “멤버를 확인하고 false를 주는 곳에서”였다. AI가 반례를 냈다. 방 관리자의 `leave`는 전체 락 안이라, 받는 쪽 버퍼가 차 있으면(실험 3) 서버 전체가 최대 약 20초 멈출 수 있다. 실패 지점마다 오류 형식 코드가 흩어지는 문제도 있다.

그래서 내가 물었다. “비멤버는 결국 인가 확인인데 handleText에서 하는 게 맞나”. AI는 판단과 알려 주기를 나누자고 제안했다. 판단을 핸들러로 옮기면 확인과 퍼뜨리기 사이에 `LEAVE`·끊김이 끼어들므로(P1-3·4), 판단은 락 안에 두고 결과(`boolean`)만 돌려준다. 알려 주기는 세 실패가 모두 돌아오고 락을 쥐지 않은 `handleTextMessage`에서 한다. 나는 “판단은 저기서 하지만 이 return 값을 결국 맨 위 handleText에서 받아서 돌려주는 입출 창구인 거죠?”라고 내 이해를 확인했다.

나머지 결정은 ADR-0011에 남겼다.

- Java 표현: 내 답은 “타입별 record”. 오류 종류마다 record를 두면 각 생성자가 자기 필수 필드를 검사한다.
- JSON: `type`은 `ERROR` 하나, 종류는 `code`(AI 제안에 동의). 오류마다 `type`을 다르게 하면 옛 클라이언트는 처음 보는 오류를 오류인지도 모른다.
- 깨진 JSON에 연결 유지: “A 유지입니다. 실수 한 번에 끊기면 안 되니까요”. AI 보충으로, 메시지 경계는 Tomcat이 프레임으로 나눠 두므로 다음 프레임은 읽을 수 있다.
- 잡는 예외: “A입니다. 서버 버그는 1011이 맞으니까요”. `InvalidMessageException`만 잡고, 예상 못 한 예외는 지금처럼 1011로 닫는다.

실제로 나가는 응답은 이렇다.

```json
{"type":"ERROR","requestType":"SEND","roomId":"X","message":"방 X의 멤버가 아니다. 먼저 JOIN해야 한다","code":"NOT_MEMBER"}
{"type":"ERROR","message":"잘못된 메시지: Unexpected end-of-input within/between Object entries","code":"INVALID_MESSAGE"}
```

`NOT_MEMBER`는 원인이 방이라 `requestType`과 `roomId`를 담고, `INVALID_MESSAGE`는 원인이 내용이라 담지 않는다. 기준은 '이걸 고치려면 무엇을 알아야 하나'다.

## 결정 2: 상태가 아니라 행동으로 살아 있음을 확인한다

유령을 서버가 스스로 알아채려면? 내 첫 답은 “서버가 주기적으로 체크하면 될 것 같습니다.”였다. AI의 반례: 주기적으로 `isOpen()`을 들여다봐도 유령은 `true`다(실험 1). 상태가 아니라 행동, 즉 ping을 보내고 pong이 오는지로 확인해야 한다. 1편에서 정해 둔 ping/pong(ADR-0005)과 같은 결론이었고, 그때 미룬 값을 이번에 정했다.

**값.** 먼저 AI가 반례를 냈다. 지하철 터널에서 5초 끊기는 사용자를 1초 주기·2초 타임아웃으로 보면 살아 있는 연결을 끊는다. 이어진 AI의 비교는 이랬다. 유령을 늦게 찾는 것은 서버 자원 문제지만, 살아 있는 사용자를 끊으면 사용자가 느끼고 메시지를 놓친다. 그러니 타임아웃은 넉넉하게 잡는다. 반대로 너무 드물게 보내면 프록시 유휴 타임아웃(Nginx 기본 60초, AI의 일반 설명이며 이 프로젝트에서 확인하지 않음)에 정상 연결이 끊기므로 주기는 60초보다 짧아야 한다. 이 비교를 듣고 내가 정한 값이 “주기 30초, 타임아웃 90초로 하겠습니다”다.

**판정.** heartbeat는 스케줄러 스레드 하나가 세션을 차례로 돌며 ping을 보낸다. ping도 같은 세션에 쓰는 전송이라 전송 입구의 세션 락을 거치는데, 버퍼가 찬 유령의 락에서는 최대 약 20초 기다릴 수 있다(실험 3). AI의 반례(어림셈)는 그런 유령이 5명이면 그 뒤에 줄 선 세션들의 ping이 약 100초 늦게 간다는 것이었다. 기준이 '마지막 pong 이후 90초'라면 ping을 늦게 받은 멀쩡한 세션도 pong할 기회 없이 90초를 넘긴다. 내 답은 “타임아웃 넘어서 멀쩡한 D도 끊길 것 같습니다”였다(여기서 D는 실험 3의 D가 아니라 뒤에 줄 선 멀쩡한 세션을 가리킨다).

막는 방법으로 나는 “막힌 C는 기다리지 않고 건너뛰면 될 것 같습니다”라고 답했다. 그런데 `synchronized`는 기다릴지 말지 고를 수 없어서, 건너뛰려면 전송 입구 전체를 `ReentrantLock.tryLock`으로 바꾸고 세션마다 락을 보관해야 한다. AI가 대안으로 판정 기준 변경을 내놓았고, 나는 그쪽을 골랐다. 기준은 **'ping을 보낸 뒤 90초 동안 pong 없음'**이다. ping이 늦게 가도 멀쩡한 세션이 끊기지 않고 전송 입구도 그대로다. 대가로 막힌 세션이 많으면 유령 판정이 늦어질 수 있고, 유령은 확인 간격 때문에 최대 약 120초 뒤 정리된다.

**시각 보관.** heartbeat 안에 Map을 두면? 내 답은 “끊길 때 맵에서 지워야 합니다”였다. AI가 세션 attributes에 두는 대안을 냈다. 세션과 함께 사라지고, `javap`로 보니 Spring 세션의 attributes는 `ConcurrentHashMap`이라 여러 스레드가 써도 안전하다. 내 선택은 이쪽이었다. “지울 필요가 없으니까요”.

**닫기만 한다.** heartbeat는 응답 없는 세션을 닫기만 하고, 정리는 Spring이 부르는 `afterConnectionClosed` 한 경로에서 한다. ping과 닫기도 같은 세션에 쓰는 전송이라 전송 입구(`SessionSender`)를 거친다. 이 구성은 AI가 제안하고 내가 동의했다.

## 검증: 고치기 전 4개 실패, 고친 뒤 6개 통과

시나리오 6개를 Java 테스트로 만들고, 고치기 전에 먼저 돌렸다. 내 예상은 1 실패 / 2 통과 / 3 실패 / 4 실패 / 5 실패 / 6 통과였고, 실행 결과 6개 모두 예상과 일치했다.

| # | 시나리오 | 고치기 전 | 고친 후 |
|---|---|---|---|
| 1 | pong 안 하는 유령(TCP 직접 연결) | 3초 뒤에도 매핑에 남음 | 정리됨 |
| 2 | pong하는 조용한 클라이언트 | 통과 | 3초 동안 안 끊김 |
| 3 | 깨진 JSON | 1011로 닫힘 | `INVALID_MESSAGE`, 연결 유지 |
| 4 | 비멤버 `SEND` | 응답 없음 | `NOT_MEMBER` |
| 5 | 비멤버 `LEAVE` | 응답 없음 | `NOT_MEMBER` |
| 6 | 서버 버그 예외 | 통과 | 1011 유지 |

테스트에서는 주기 200ms·타임아웃 600ms로 덮어썼고, 유령은 `pong 없음 613ms → 닫음` 로그 뒤 두 매핑에서 정리됐다. 전체 테스트 62개는 3회 모두 통과했다.

시나리오 2·6은 고치기 전에도 통과해서 실패를 본 적이 없다. 그래서 구현을 일부러 망가뜨려 확인하고 되돌렸다. 변이 A(pong 기록 삭제)에서는 시나리오 2가 실패해 조용한 클라이언트가 끊겼고, 변이 B(모든 `RuntimeException`을 잡아 오류 응답)에서는 시나리오 6이 1011을 받지 못해 실패했다. 두 테스트가 각각 '살아 있는 연결을 끊지 않는다'와 '서버 버그를 클라이언트 잘못으로 덮지 않는다'를 지킨다.

## 남은 것과 배운 것

- 진짜 유령(ACK 없음)은 재현하지 못했다. 닫기도 세션 락 안에서 Close 프레임을 쓰므로, 그런 유령이면 쓰기 시간 초과까지 스케줄러가 막힐 수 있다. 확인 필요, P1-8에서 함께 본다.
- 유령 때문에 방이 약 20초 멈추는 문제는 해결하지 않았다(P1-8).
- 같은 방 `SEND` 두 개의 오류는 구별할 수 없다. 클라이언트가 만든 메시지 id가 필요해 P3(멱등성)로 미뤘다.
- 계속 잘못된 입력을 보내는 클라이언트도 연결이 유지된다. 내 판단은 Rate limit의 책임이라는 것이어서 P9로 미뤘다.

배운 것은 이 한 줄이다. “계층을 나눠서 봐야 한다는 점을 배웠습니다.” 세 문제는 생기는 곳과 보이는 곳의 관계가 저마다 달랐고, 계층 지도를 그리고 나서야 끊김·버퍼·예외 처리가 이해됐다.

## 직접 해 보기

자기 WebSocket 서버에서 클라이언트 프로세스를 `kill -STOP`으로 멈춰 보고 `afterConnectionClosed`가 언제 불리는지 로그로 확인해 보자. 깨진 JSON도 한 번 보내 보고 클라이언트가 받는 닫힘 코드와 reason을 찍어 보자.

## 용어 정리

- 세션 저장소(`SessionRegistry`): 연결된 세션 전체 목록, heartbeat가 도는 대상
- 방 관리자(`RoomRegistry`): 방 ↔ 세션 두 매핑, 전체 락
- 브로드캐스터(`RoomBroadcaster`): 방 멤버에게 보내기, 방 락
- 전송 입구(`SessionSender`): 텍스트·ping·닫기 등 쓰기의 유일한 입구, 세션 락
- 핸들러(`ChatWebSocketHandler`): 연결·메시지·끊김 이벤트를 받는 입출력 창구
- 유령 세션: FIN·RST·Close 없이 클라이언트가 사라져 서버 매핑에 남은 세션
- 느린 소비자: 받는 속도가 느린 클라이언트(P1-8)
