keepup은 Spring Boot와 MySQL로 만드는 학습 프로젝트이고, 이 글은 그 운영기의 넷째 날 기록이다. 요청 하나를 클라이언트(curl)에서 구간별로 쪼개 재고, 서버 필터가 찍은 시간과 나란히 놓아 봤다.

**요약**
1. 재기동 직후 첫 `/actuator/health` 요청은 curl wait(요청을 보내기 직전부터 응답 첫 바이트까지) 기준 약 181ms였다. 그중 서버 필터 안이 86ms, 필터 밖이 약 95ms였다. 두 번째·세 번째 요청도 10.51ms, 8.30ms였고, 네 번째 요청부터 약 2.5ms로 안정됐다.
2. 첫 요청에서도 TCP 연결은 0.23ms로 다른 요청과 같았다. 첫 요청이 느린 이유는 TCP 연결이 아니었다.
3. TCP 연결은 OS 커널이 맺고, 톰캣은 그 연결을 `accept()`로 꺼내 가면서부터 손댄다(일반적으로 알려진 TCP 동작).
4. `localhost`는 `127.0.0.1`이 아니라 `::1`(IPv6)로 연결됐다. 각 10회 1묶음에서 두 주소의 wait 범위는 비슷했다(2.47~4.02 대 2.51~4.00). `127.0.0.1` 첫 회만 7.61ms였다.

**읽는 법:** 숫자는 macOS 로컬에서 묶음당 한 번 실행해 잰 값이다. 잰 것이 아닌 부분(일반적으로 알려진 동작, 추론, 가설)은 그 자리에 따로 밝힌다.

## 1. 무엇이 궁금했나

요청이 TCP 연결부터 톰캣이 처리하기까지 실제로 어떤 과정을 거치는지 알고 싶었다. 특히 그중 어디까지가 OS 커널의 일이고 어디부터가 톰캣의 일인지 정확히 나누고 싶었다.

그래서 curl 구간 측정 스크립트를 만들어 `/actuator/health`를 쟀다. 응답 헤더의 requestId로 curl 결과와 서버 필터(`RequestLogFilter`) 로그를 짝지었다. curl이 잰 시간과 서버 로그 시간의 차이가 어느 구간에서 생기고, localhost에서는 얼마나 되는지 보는 것이 목표였다.

## 2. 따라간 요청

### curl 시간 변수는 누적값이다

`curl -w`로 찍는 시간 변수는 모두 curl이 시작한 시점부터 잰 누적값이다. 구간 시간은 뺄셈으로 만든다.
- `pretransfer`: 요청을 보내기 직전
- `starttransfer`: 응답의 첫 바이트를 받은 시점

스크립트(`scripts/curl-timing.sh`)는 이렇게 나눴다.

| 열 | 계산 | 뜻 |
|---|---|---|
| dns | `namelookup` | 이름 → IP 주소 |
| tcp | `connect - namelookup` | TCP 3-way handshake |
| tls | `appconnect - connect` | HTTPS일 때만 (http면 0) |
| wait | `starttransfer - pretransfer` | 요청을 보내기 직전부터 첫 응답 바이트까지 |
| body | `total - starttransfer` | 나머지 응답 수신 |

서버 로그의 ms와 비교할 대상은 `total`이 아니라 `wait`다. DNS와 TCP 연결은 요청을 보내기 전에 끝나서 서버 필터와 겹치지 않기 때문이다.

### 요청 하나의 길

먼저 용어 몇 개(DAY 003에서 정리한 것):
- **accept 큐(backlog)**: OS 커널이 handshake를 끝낸 연결을 서버 프로그램이 꺼내 갈 때까지 쌓아 두는 줄.
- **Poller**: 톰캣이 받아 둔 연결들을 지켜보다가, 요청 데이터가 도착한 연결을 찾아 스레드 풀에 일을 넘기는 톰캣 스레드.
- **작업 큐**: 스레드 풀에 넘어간 일이 서는 줄. 쉬는 스레드가 있어도 대개 이 줄을 거치고, 스레드가 다 바쁘면 여기서 기다린다.

SYN · SYN-ACK · ACK는 TCP 연결을 맺을 때 클라이언트와 서버가 주고받는 세 번의 신호다(3-way handshake).

```
 curl                         OS 커널 (서버 쪽)              톰캣
 ────                         ─────────────────              ────
 DNS (localhost → 주소)
 SYN      ────────────▶      SYN 받음
          ◀────────────      SYN-ACK
 ACK      ────────────▶      handshake 끝 → accept 큐에 넣음
 connect ● (tcp 끝)                 │
                                    └──────────────▶  ① accept() (시점은 재지 않음)
 pretransfer ●
 요청 전송 ────────────▶     데이터 도착  ──────────▶  ② Poller → 작업 큐 (스레드가 바쁘면 대기)
                                                      ③ 워커 스레드가 HTTP 요청을 읽어 해석
                                                      ④ 내 필터보다 앞선 필터들
                                                      ┌───────────────────────────┐
                                                      │ RequestLogFilter start    │ ← 서버 로그 ms
                                                      │ 컨트롤러 · DB 체크         │
                                                      │ finally: 로그 기록        │
                                                      └───────────────────────────┘
                                                      ⑤ 응답 마무리 · 소켓 쓰기
 starttransfer ● ◀──────────────────────────────────  첫 바이트
 total ●
```

이 그림은 측정이 아니다. ①과 ②의 작업 큐는 DAY 003에서 읽은 톰캣 소스(`NioEndpoint`, `Acceptor`, `TaskQueue`)를, ②의 Poller 동작은 일반적으로 알려진 구조를 바탕으로 했고, ③~⑤는 일반적인 서블릿 처리 순서로 이해한 것이다.
- ②~④는 필터 밖이면서 `wait` 안에 있다.
- ①은 요청 데이터가 오기 전에 일어날 수도 있어서, `wait`에 들어가는지는 재지 않았다.
- ⑤는 그림에서 필터 뒤에 뒀지만, 응답 첫 바이트가 필터의 `finally`보다 먼저 나갈 수도 있다. 이것도 확인하지 않았다.

이 글에서는 응답 첫 바이트가 필터의 `finally` 뒤에 나간다고 가정하고, `wait − 서버 로그`를 "필터 밖" 시간이라고 부른다.

## 3. 측정값

환경: macOS, localhost, Spring Boot 4.1.1, curl 8.7.1. 앱을 재기동한 직후부터 쟀고, 묶음마다 한 번씩 실행했다. 단위는 ms.

### 재기동 직후 첫 요청 + 이후 10회 (`localhost`)

| 순서 | curl wait | 서버 로그 | 필터 밖 (wait − 서버 로그) |
|---|---|---|---|
| 재기동 후 첫 요청 | 180.81 | 86 | 약 95 |
| 2 | 10.51 | 9 | 약 1.5 |
| 3 | 8.30 | 7 | 약 1.3 |
| 4~11 | 2.44~2.84 | 1~2 | 약 0.7~1.7 |

- 서버 로그는 소수점을 버린 정수 ms라 이 차이는 최대 1ms 작을 수 있다. 4행부터는 차이가 이 오차와 비슷한 크기다.
- dns 0.01, tcp 0.20~0.24, tls 0이었다. 첫 요청의 tcp도 0.23으로 다른 요청과 같았다.
- 11건 모두 응답 헤더의 `X-Request-Id`와 서버 로그의 requestId가 맞았다.

### `127.0.0.1` vs `localhost` (위 11건 이후, 각 10회)

| 주소 | curl이 연결한 ip | dns | tcp | wait | 서버 로그 |
|---|---|---|---|---|---|
| `127.0.0.1` | 127.0.0.1 | 0.06~0.10 | 0.19~0.23 | 2.47~4.02 (첫 회 7.61) | 1~3 (첫 회 6) |
| `localhost` | ::1 | 0.01 | 0.19~0.27 | 2.51~4.00 | 1~3 |

### 측정 전에 적은 예측과 비교

DAY 002는 curl total에서 필터 시간을 뺀 값(total − 필터)을 필터 밖으로 불렀으므로, 첫 행의 비교만 total 기준으로 맞췄다. 위 표의 약 95가 여기서 약 96이 되는 이유다.

| 내 예측 | 결과 |
|---|---|
| 첫 요청은 DAY 002 실험과 비슷할 것 | DAY 002의 `health` 첫 요청(2회)은 curl total 146.5~159.7ms, 그중 필터 밖 약 76~84ms였다. 오늘은 같은 total 기준으로 182.49ms, 필터 밖 약 96ms였다. 오늘이 더 느렸다(표본이 1회·2회라 일반화하지 않는다) |
| 두 번째부터 차이가 작아질 것 (클래스 로딩이 줄어서) | 방향은 맞았다. 이유는 재지 않았다 |
| `localhost`는 `127.0.0.1`로 연결될 것 | 틀렸다. 재기동 후 `localhost`로 보낸 21건 모두 `::1`(IPv6)이었다 |

## 4. 배운 것: TCP 연결과 accept의 순서

### TCP 연결은 OS가 맺고, 톰캣은 accept()부터 손댄다

3-way handshake(SYN → SYN-ACK → ACK)는 톰캣이 아니라 OS 커널이 한다. 커널은 연결을 다 맺어 accept 큐에 넣어 두고, 톰캣은 `accept()`로 그걸 꺼내 간다. 그래서 curl의 connect가 끝나는 게 먼저고 톰캣의 accept는 그 뒤다. 이건 오늘 잰 것이 아니라 일반적으로 알려진 TCP 동작이다. DAY 003에서 connect가 즉시 끝난 요청이 accept 큐에 있었다고 추론한 것과도 어긋나지 않는다.

내가 이해한 바로는(OS마다 다를 수 있고 확인하지 않았다), 어디서 막히느냐에 따라 늘어나는 열이 다르다.

| 어디가 막혔나 | 늘어나는 열 |
|---|---|
| accept 큐가 꽉 참 → handshake가 끝나지 못함 | `tcp` |
| 요청 데이터가 온 뒤 톰캣 안에서 늦음 (예: 스레드가 다 바빠 작업 큐에서 대기) | `wait` |

DAY 003 실험(1회)에서는 connect가 2.2~6.1초 늦어졌다. accept 큐가 차서 그랬다는 건 tcpdump(오가는 패킷을 직접 찍어 보는 도구)로 확인하지 않은 가설이고, macOS에서 표 첫 행처럼 동작하는지도 확인하지 않았다.

처음에 나는 accept가 connect 전이라고 답했다가 고쳤다. 헷갈렸다.

### 첫 요청의 느림은 필터 안팎 양쪽에 있었다

첫 요청에서 필터 안이 86ms, 필터 밖이 약 95ms였다. 처음에는 TCP 연결 시간이 원인일 거라고 생각했지만, total 182.49ms 중 TCP는 0.23ms여서 이 가설은 기각됐다. 참고로 wait 기준 95ms에는 TCP가 애초에 들어가지 않는다. 필터 밖 95ms의 후보는 ② Poller·작업 큐, ③ HTTP 요청 해석, ④ 앞선 필터, ⑤ 응답 마무리다(① accept는 `wait`에 들어가는지부터 모른다). 나눠 재지는 않았다.

어디서 왔을지는 아직 따로 추측하지 못했다.

### `::1`은 IPv6의 "나 자신"이다

- `127.0.0.1`(IPv4)과 `::1`(IPv6)은 둘 다 루프백 주소, 즉 밖으로 나가지 않고 내 컴퓨터로 돌아오는 주소다. 형식만 다르고 뜻은 같다. `::1`은 `0000:…:0001`에서 연속된 0을 줄여 쓴 것이다(IPv6 표기 규칙으로 알려진 내용).
- 내 `/etc/hosts`에는 `localhost`가 두 주소에 모두 연결돼 있었고, curl은 `::1`로 연결했다. 왜 IPv6가 먼저 골라졌는지는 확인하지 않았다.
- `lsof`(어떤 프로세스가 어떤 포트를 열었는지 보는 명령)로 보니 자바는 8080을 IPv6 소켓 하나로만 열고 있었다(`IPv6 TCP *:8080 (LISTEN)`). IPv4 소켓이 따로 없었으니 `127.0.0.1` 요청도 이 소켓이 받은 것으로 본다. IPv6 소켓은 IPv4 연결도 함께 받도록 열릴 수 있다(듀얼 스택, 일반적으로 알려진 동작이고 이 환경에서 확인하지는 않았다).

## 5. 막힌 것 / 다음에 볼 것

- **첫 요청의 필터 밖 약 95ms가 어느 구간인지 모른다.** ②~⑤를 나눠 재야 한다.
- **응답 첫 바이트가 필터의 `finally`보다 먼저 나가는지 모른다.** 그렇다면 "wait − 필터 시간"을 필터 밖 시간으로 읽을 수 없다.
- **서버 로그가 정수 ms다.** `/ 1_000_000`에서 소수점이 잘려서, 안정된 뒤의 "필터 밖 약 1ms"는 오차 범위 안이다. μs로 찍어야 비교할 수 있다.
- **처음 몇 요청이 느린 구간(웜업)이 첫 요청 하나로 끝나지 않았다.** 2, 3번째도 10ms, 8ms였고 4번째부터 약 2.5ms로 안정됐다. 이유는 모른다.
- **`127.0.0.1`의 dns가 `localhost`보다 길었다**(0.06~0.10 vs 0.01). 숫자 주소인데도 그랬다. 이유는 확인하지 않았다(차이는 0.1ms 미만).
- **`127.0.0.1` 첫 회만 7.61ms(서버 로그 6ms)로 느렸다.** 이유는 확인하지 않았다.
- **처리 스레드가 exec-2, 4, 6, 8, 10 순으로 짝수 번호만 돌았다.** 이유는 모른다.
- 모든 값은 묶음당 1회 실행이다.
