RFC 스펙과 구현체를 공부하면서 HTTP 상태 코드와 API 계약을 혼동하고 있었다는 것을 알게 되었다.

처음에는 존재하지 않는 사용자를 조회하면 당연히 404가 반환되어야 한다고 생각했다. 그런데 실제 Spring 코드에서 예외를 발생시키면 500이 반환될 수도 있다.

왜 이런 차이가 발생하는지 이해하기 위해 RFC에서 정의하는 HTTP 상태 코드와 우리가 작성하는 API 계약을 구분해 봤다.

## RFC와 API 계약은 무엇이 다를까?

처음에는 RFC와 API 계약이 서로 다른 개념이라고 생각했다. 하지만 둘 다 어떤 동작을 해야 하는지 정의한다는 점에서는 스펙(명세)에 해당한다.

차이는 무엇에 대한 규칙을 정의하는가에 있다.

**RFC는 프로토콜의 공통 규칙을 정의한다.** 예를 들어 HTTP RFC에서는 404와 500이라는 상태 코드가 어떤 의미인지 정의한다.

**API 계약은 특정 서비스가 제공할 동작을 정의한다.** 예를 들어 사용자 조회 API에서 요청한 사용자가 없으면 404를 반환하기로 정할 수 있다.

즉, RFC가 상태 코드의 의미를 정의한다면 API 계약은 그 상태 코드를 어떤 상황에 사용할지 구체적으로 정한다.

처음에는 RFC에 상태 코드가 정의되어 있으니 사용자 조회 실패 같은 상황에서도 자동으로 알맞은 코드가 반환될 것이라고 생각했다. 하지만 RFC는 우리 서비스의 사용자 데이터나 비즈니스 예외를 알지 못한다. 원하는 응답을 보장하려면 API 계약을 정하고, 애플리케이션에서 그 계약에 맞게 결과와 예외를 HTTP 응답으로 연결해야 한다.

## 사용자 조회 API로 살펴보기

다음과 같은 API가 있다고 가정하자.

```http
GET /users/999
```

999번 사용자는 데이터베이스에 존재하지 않는다. 우리 API 계약에서는 다음과 같이 정의했다고 가정한다.

| 상황 | 응답 |
|---|---|
| 사용자가 존재함 | 200 OK |
| 사용자가 존재하지 않음 | 404 Not Found |

그런데 실제로 요청했더니 500이 반환되었다.

처음에는 존재하지 않는 사용자를 조회했으니 404가 반환되어야 하는데, 왜 500이 나오는지 이해되지 않았다.

이 상황을 구분해 보면 다음과 같다.

- **기대한 결과:** API 계약에 따라 404 반환
- **실제 결과:** 500 반환
- **확인할 대상:** 사용자 조회 로직과 예외 처리 구현
- **확인할 문제:** API 계약과 실제 동작이 일치하지 않는 이유

여기서 중요한 것은 **RFC가 `/users/999`의 응답을 직접 결정하는 것은 아니라는 점**이다.

RFC는 404라는 상태 코드의 의미를 정의할 뿐, 우리 서비스의 999번 사용자가 존재하는지는 알지 못한다.

## Spring에서는 왜 500이 반환될까?

다음 Controller를 살펴보자.

```java
@GetMapping("/users/{id}")
public String getUser(@PathVariable Long id) {
    if (id == 999) {
        throw new RuntimeException("사용자 조회 실패");
    }

    return "OK";
}
```

999번 사용자 조회 요청이 들어오면 `RuntimeException`이 발생한다.

별도의 예외 처리 설정이 없는 일반적인 Spring Boot 환경에서는 처리되지 않은 예외가 최종적으로 500 응답으로 이어질 수 있다.

그 이유는 Java에서 `RuntimeException`이 발생했다고 해서 Spring이 자동으로 사용자가 존재하지 않는 상황이라고 판단하는 것은 아니기 때문이다. Spring 입장에서는 이 예외가 어떤 비즈니스 의미인지 별도의 정보가 없다.

예를 들어 다음과 같이 사용자 미존재 예외를 만들었다고 해 보자.

```java
public class UserNotFoundException extends RuntimeException {
    public UserNotFoundException(Long id) {
        super("사용자를 찾을 수 없습니다: " + id);
    }
}
```

그리고 예외가 발생했을 때 404를 반환하도록 처리할 수 있다.

```java
@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(UserNotFoundException.class)
    public ResponseEntity<Void> handleUserNotFound() {
        return ResponseEntity.notFound().build();
    }
}
```

이렇게 처리하면 `UserNotFoundException`이 발생했을 때 HTTP 404 응답을 반환할 수 있다.

정리하면 다음과 같다.

- RFC는 404의 의미를 정의한다.
- API 계약은 사용자가 없으면 404를 반환하기로 정한다.
- Spring 애플리케이션은 해당 상황을 404 응답으로 변환하도록 구현한다.

## 실행 흐름을 추적한다는 것은?

처음에는 실행 흐름을 추적한다는 말도 막연했다.

이번 예시에서는 요청이 들어왔을 때 어떤 코드를 거쳐 응답이 결정되는지 확인하는 과정이라고 이해했다.

예외 처리를 따로 설정하지 않은 경우의 흐름을 단순화하면 다음과 같다.

```text
클라이언트
    |
    | GET /users/999
    v
Tomcat
    |
    | HTTP 요청 처리
    v
Spring DispatcherServlet
    |
    | Controller 호출
    v
UserController.getUser(999)
    |
    | RuntimeException 발생
    v
Spring MVC 예외 처리
    |
    | 404로 매핑하는 처리 없음
    v
서버 오류 처리
    |
    v
HTTP 500 응답
```

이때 Tomcat은 HTTP 요청을 받아 Spring으로 전달하고, Spring MVC는 적절한 Controller를 찾아 실행한다.

Controller에서 예외가 발생하면 Spring MVC의 예외 처리 과정으로 전달된다. `@ExceptionHandler`와 같은 처리가 있다면 예외를 원하는 HTTP 응답으로 변환할 수 있다.

하지만 적절한 예외 처리가 없다면 서버 오류 응답으로 이어질 수 있다.

이 과정을 로그나 디버거로 확인하면 예외가 어디에서 발생했는지, 어떤 처리 과정을 거쳤는지 추적할 수 있다.

여기서 내가 확인해야 할 것은 단순히 500이 반환되었다는 결과가 아니다. **왜 404를 기대했는지, 실제 코드에서는 어떤 처리를 했는지, 어디에서 그 차이가 발생했는지** 확인해야 한다.

## RFC를 확인해야 하는 경우는 언제일까?

그렇다면 API에 문제가 발생할 때마다 RFC를 확인해야 할까? 그럴 필요는 없다.

예를 들어 사용자 조회 API가 404 대신 500을 반환했다면 먼저 API 계약과 애플리케이션의 예외 처리 코드를 확인하는 것이 적절하다.

반대로 HTTP 204 응답에 메시지 본문을 포함해 전송하는 문제가 발생했다면 HTTP 프로토콜 규칙을 확인해야 한다. RFC에서는 204 응답에 메시지 본문을 포함하지 않도록 정의하기 때문이다.

예를 들어 삭제 API가 성공했을 때 다음 응답을 실제 네트워크로 보냈다고 가정하자.

```http
HTTP/1.1 204 No Content
Content-Type: application/json

{"message": "삭제 성공"}
```

이때 문제는 단순히 우리 API 계약에서 204를 반환하기로 했는지가 아니다. **204 응답에는 본문을 포함할 수 없다는 HTTP 공통 규칙 자체**와 어긋난다는 점이다.

다만 애플리케이션 코드에서 본문 객체를 생성했다는 사실만으로 실제 전송까지 이루어졌다고 단정할 수는 없다. 프레임워크나 서버가 본문을 제거했을 수도 있으므로 실제 HTTP 응답을 확인해야 한다.

이렇게 구분해 보니 두 문제의 출발점이 달랐다.

- **404 대신 500이 반환됨:** API 계약에서 약속한 결과가 구현됐는지 확인한다.
- **204 응답에 본문이 실제 전송됨:** HTTP RFC의 규칙과 실제 응답 처리 과정을 비교한다.

또한 API 계약은 HTTP 규칙을 무시하고 작성할 수 있는 별개의 약속이 아니다. API 계약도 사용하는 프로토콜의 규칙을 지켜야 한다.

두 상황은 서로 다른 문제다.

| 문제 | 먼저 비교할 대상 |
|---|---|
| 없는 사용자 조회 시 500 반환 | API 계약과 Spring 예외 처리 |
| HTTP 204 응답에 본문이 전송됨 | HTTP RFC와 실제 HTTP 응답 처리 |
| WebSocket Ping에 Pong 응답이 없음 | WebSocket RFC와 실제 프레임 처리 |

결국 어떤 문제가 발생했는지에 따라 확인해야 할 규칙과 구현 코드가 달라진다.

## 정리

이번에 공부하면서 RFC와 API 계약을 구분할 수 있게 되었다.

처음에는 RFC가 HTTP 상태 코드를 정의했기 때문에 존재하지 않는 사용자를 조회하면 당연히 404가 나와야 한다고 생각했다.

하지만 RFC는 404의 의미를 정의하는 것이고, 우리 서비스에서 어떤 상황에 404를 반환할지는 API 계약과 구현에서 결정한다.

반대로 API가 204를 선택했다면 응답 본문을 보내지 않는 등의 HTTP 규칙도 따라야 한다. **API 계약을 지키는 것과 HTTP 프로토콜 규칙을 지키는 것은 서로 다른 확인 항목이지만, 둘 다 만족해야 한다.**

앞으로 예상과 다른 동작이 발생하면 다음 순서로 확인해 보려고 한다.

1. 내가 기대한 결과는 무엇인가?
2. 그 결과는 어디에 정의되어 있는가?
3. RFC의 프로토콜 규칙인가, 우리 서비스의 API 계약인가?
4. 실제 구현에서는 어떤 코드를 실행했는가?
5. 기대한 결과와 실제 결과가 달라진 이유는 무엇인가?

이전에는 API를 사용하거나 구현할 때 기대하는 동작의 근거가 어디에 있는지 깊이 생각하지 않았다.

이제는 문제가 발생했을 때 바로 코드를 수정하기보다는 **어떤 규칙이나 계약을 지키지 못한 것인지 먼저 확인해 봐야겠다.** 그리고 그 계약이 실제 코드에서 어떻게 구현되어 있는지 실행 흐름을 따라가며 확인하는 습관을 들이려고 한다.
