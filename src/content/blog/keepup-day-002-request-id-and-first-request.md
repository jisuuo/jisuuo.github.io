keepup은 Spring Boot와 MySQL로 만드는 학습 프로젝트이고, 이 글은 그 운영기의 둘째 날 기록이다. 요청마다 requestId와 처리 시간을 로그로 남기는 필터를 만들고, 그 로그로 "앱을 재기동한 직후의 첫 요청만 왜 느린가"를 따라가 봤다.

**요약**
1. 재기동 직후 첫 요청은 curl 기준 약 105~160ms가 걸렸다. 두 번째 요청부터는 서버 안쪽 시간이 3~16ms로 줄었다.
2. "DB를 확인하느라 느릴 것"이라는 내 예측은 틀렸다. DB를 확인하지 않는 `liveness` 경로도 첫 요청에서는 느렸다.
3. 첫 요청에서 처음 쓰는 클래스가 대량으로 로드되는 것을 관찰했다. 유력한 후보지만 로드에 걸린 시간은 재지 못했다.

## 1. 무엇이 궁금했나

오늘의 질문은 로드맵 체크리스트의 Q2("서버 안에서 누가 처리하지?", 스레드와 커넥션 풀 관련)였다. DB를 내려 둔 동안 응답이 오래 걸렸다면, 그동안 요청을 붙잡고 있던 건 누구일까? 다만 로드맵 2주차 항목은 "풀 기본값 확인"까지여서, 오늘은 HikariCP(JDBC 커넥션 풀 라이브러리)의 기본값과 측정 기반까지만 봤고 DB를 내리는 실험은 하지 않았다.

먼저 요청마다 시간을 재는 도구가 필요했다. 그래서 필터를 만들었다.

## 2. 요청마다 requestId와 시간을 남기는 필터

필터(Filter)는 서블릿 컨테이너가 요청을 받자마자 거치는 처리 단계라서, 모든 요청의 입구와 출구를 한 곳에서 감쌀 수 있다. 여기서 MDC(현재 스레드에 붙는 key-value 보관함)에 requestId를 넣어 두면, 같은 스레드가 찍는 모든 로그 줄에 requestId가 자동으로 붙는다. 톰캣은 스레드를 재사용하므로 요청이 끝나면 `finally`에서 지워야 한다. (여기까지는 일반적으로 알려진 동작을 정리한 것이고, 이번 실험으로 따로 확인한 것은 아니다.)

요청마다 8자리 requestId를 만들어 MDC에 넣고 응답 헤더 `X-Request-Id`로도 돌려준다. 요청이 끝나면 걸린 시간을 한 줄로 남긴다(커밋 `03e3895`, 발췌이며 일부 줄을 단순화했다).

```java
MDC.put("requestId", requestId);
response.setHeader("X-Request-Id", requestId);
long start = System.nanoTime();
try {
    chain.doFilter(request, response);
} finally {
    long elapsedMs = (System.nanoTime() - start) / 1_000_000;
    log.info("{} {} -> {} {}ms", method, uri, response.getStatus(), elapsedMs);
    MDC.remove("requestId");
}
```

실제로 찍힌 로그 한 줄이다(13:43에 재기동한 실행, 포트는 8080이 사용 중이어서 8081). `exec-1`은 톰캣 워커 스레드의 이름이다.

```
13:43:44.309 [http-nio-8081-exec-1] [2c12f355] INFO  ...RequestLogFilter - GET /actuator/health/liveness -> 200 49ms
```

## 3. 첫 요청은 얼마나 느렸나

앞으로 이 세 가지 말을 쓴다.

- **필터 안**: 우리 필터가 잰 시간(위 로그의 `49ms`).
- **curl total**: `curl`이 요청을 보내고 응답을 다 받을 때까지의 시간.
- **필터 밖**: curl total에서 필터 안을 뺀 나머지. 연결, 필터 시작 전 구간, 응답을 쓰고 받는 시간이 모두 들어간다.

그리고 요청 경로 두 가지를 비교했다. `/actuator/health/liveness`는 DB 확인이 없고, `/actuator/health`는 DB 연결 확인을 포함해 여러 항목을 함께 확인한다(후자의 구성은 일반적으로 알려진 동작이다). 이하 `liveness`, `health`로 쓴다.

13:43 실행에서 재기동 직후 `liveness`를 첫 요청으로 보냈을 때의 시간 흐름이다.

```
13:43:44.200  curl이 요청을 보냄          ← 추정: 44.309 + 응답쓰기(약 1ms, 가정) − 110ms로 역산
   ↓ 약 50ms   (이 구간에는 로그가 없음)
13:43:44.250  DispatcherServlet 초기화 시작   (스프링 MVC의 요청 진입점 서블릿)
13:43:44.252  초기화 끝
   ↓ 약 8ms
13:43:44.260  필터 시작                  ← 추정: 44.309 − 49ms
13:43:44.309  필터 끝, 49ms 기록
              curl total = 110.2ms
```

| 구간 | 소요 | 구하는 법 |
|---|---|---|
| 필터 안 | 49ms | 서버 로그 |
| 필터 밖 | 약 61ms | 110.2 − 49 (정수 ms 버림 때문에 ±수 ms 오차) |
| 전체 | 110.2ms | curl total |

같은 실행의 두 번째 요청(`health`)은 curl 13.2ms, 필터 안 11ms, 필터 밖 약 2ms였다. 첫 요청에서는 필터 밖과 안이 모두 컸고, 필터에 닿기 전 약 50ms 동안은 서버 로그가 한 줄도 없었다.

## 4. "DB 확인 때문일 것"이라는 예측과 결과

**예측**: `liveness` 약 3ms, `health` 약 63ms. 첫 요청이 느린 건 DB 확인 때문이라고 봤다. 이 예측은 `liveness`와 `health`의 순서를 바꿔 보는 실험을 하기 직전에 적었다. 그 시점에는 `health`가 첫 요청일 때 61~63ms가 나온 실행이 이미 세 번 있었다.

**결과**: 여러 번 재기동하며 첫 요청과 두 번째 요청의 시간을 쟀다. 경로별로 묶으면 이렇다(실행별 원자료는 맨 아래 "측정 상세"에 있다).

| 요청 | 필터 안 | curl total |
|---|---|---|
| 첫 요청 `liveness` | 49~69ms (4회) | 105.5~124.3ms (5회) |
| 첫 요청 `health` | 61~84ms (5회) | 146.5~159.7ms (2회) |
| 두 번째 `liveness` (앞이 `liveness` 또는 `health`) | 3~6ms (4회) | 6.3~9.9ms (4회) |
| 두 번째 `health` (앞이 `liveness`) | 11~16ms (2회) | 13.2~17.9ms (3회) |
| 두 번째 `health` (앞이 `health`) | 3ms (3회) | – |

이 결과에서 읽을 수 있는 것은 다음과 같다.

- **예측한 숫자 중 `liveness` 3ms는 틀렸다.** DB 확인이 없는 `liveness`도 첫 요청일 때는 49~69ms로 느렸다. `health` 63ms는 앞선 세 번의 관찰값을 이어 적은 것이라 맞았다.
- **DB 커넥션 생성이 주된 원인으로 보이지는 않는다.** 13:35 실행에서 커넥션 풀은 첫 요청이 오기 7초 전에 이미 10/10(최대 10개가 모두 차 있음)이었다.
- **지연의 큰 몫은 "첫 요청이라는 조건"에서 나온다고 보인다.** 두 번째 `liveness`는 앞이 `liveness`든 `health`든 3~6ms로 빨랐다.
- **`health`가 첫 요청일 때 더 길었던 부분은 필터 밖에서 나왔다.** 필터 안은 `health`와 `liveness`가 비슷했다(중앙값 63ms 대 62ms). 필터 밖은 `health`가 약 76~84ms, `liveness`가 약 42~61ms였고, `health`의 값은 모두 14:24 한 묶음(2회)에서 나왔다. DB 확인은 필터 안쪽에서 실행되므로 이 차이는 DB 확인으로는 설명되지 않는다. 이유는 확인하지 못했다.
- **DB 확인의 몫이 0이라고는 말할 수 없다.** 두 번째 요청에서 처음 쓰는 `health`는 안쪽 시간이 `liveness`보다 약 5~13ms 길었다(표본 2회).

## 5. 필터에 닿기 전 구간을 클래스 로딩 로그로 들여다봤다

필터에 닿기 전 약 50ms는 로그가 없어서 무엇을 하는지 알 수 없었다. 처음 실행하는 자바 코드는 클래스를 메모리에 올리는 일(클래스 로드)이 먼저 필요하다는 점에 착안해, JVM 옵션 `-Xlog:class+load:file=<파일>:time,uptime`(클래스가 로드될 때마다 시각을 기록)을 켜고 재기동 후 `liveness` → `health`를 1회씩 보냈다(14:00 실행).

| 구간 | 길이 | 새로 로드된 클래스 |
|---|---|---|
| 유휴 (기동 완료 ~ 첫 요청 전송) | 약 5.7초 | 255개 (전부 기동 직후 1초 안) |
| 첫 요청 전송 ~ 서블릿 초기화 시작 | 약 30ms | **139개** |
| 서블릿 초기화 시작 ~ 필터 시작 | 약 10ms | 46개 |
| 필터 안 | 64ms | **328개** |
| 두 번째 요청(`health`) | 약 17ms | 27개 |

첫 요청에서 로드된 클래스는 필터 전 185개(139 + 46), 필터 안 328개, 합계 513개였고 두 번째 요청에서는 27개였다. 첫 요청 직전 2초 동안은 새로 로드된 클래스가 0개였으니, 평소 기준이 0에 가까운데 첫 요청 전 약 30ms 동안 139개가 로드된 셈이다.

이 실험으로 말할 수 있는 것은 여기까지다.

- 개수를 센 것이지 로드에 걸린 시간을 잰 것이 아니다. 개수는 처음 실행된 코드의 양을 간접으로 보여 줄 뿐이다.
- JIT 컴파일(자주 실행되는 코드를 실행 중에 최적화해 컴파일하는 JVM 기능), 스레드 생성 등 다른 "처음 한 번만" 후보는 배제하지 못했다.
- 클래스 로딩 로그와 `java -jar` 실행이 시간에 영향을 줬을 수 있다. 다만 이 실행의 첫 요청 필터 안 64ms는 다른 실행의 범위(49~84ms) 안이다.
- 구간 경계는 시각에서 계산한 추정이고(상세는 부록), 표본은 1회이다.

## 6. 배운 것

**내가 배운 것:** 요청 시간을 분석할 때 추측하고 넘어가지 않고, 먼저 측정 도구(필터 로그)를 만들어 수치로 판단하려고 했다. "첫 요청이 느린 건 DB 확인 때문"이라는 추측은 `liveness`를 첫 요청으로 보내도 느렸고 두 번째로 보내면 빨랐다는 결과로, 주된 원인이 아닌 것으로 보였다. 필터 전 구간에는 로그가 없어서, 클래스 로딩 로그를 켜고 그 구간에서 클래스가 몇 개 로드되는지 세어, 가설과 일치하는 관찰을 얻었다.

**어디까지 말할 수 있나:** 클래스가 대량으로 로드됐다는 것은 관찰됐다. 그것이 지연의 원인이라는 것은 유력한 후보다. 시간을 재지 않았으므로 확정은 아니다.

## 7. 아직 모르는 것 / 다음에 볼 것

- **필터에 닿기 전 약 50ms 동안 서버가 무엇을 하는지** 로그에는 없다(13:43 실행).
  - **내 가설:** 이 구간은 톰캣이 첫 요청에서 처음 쓰는 클래스를 로드하는 시간일 것이다.
  - **근거:** 별도 실행인 14:00 실행의 클래스 로딩 로그(§5)에서, 요청 전송부터 서블릿 초기화 시작까지 약 30ms 동안 139개가 새로 로드됐다(필터 전 전체로는 185개). 두 번째 요청은 27개였다. 가설과 일치하는 관찰이지만, 로드에 걸린 시간은 재지 않았으므로 원인으로 확정하지는 않는다.
  - **실행 간 차이:** 13:43 실행(필터 밖 약 61, 안 49ms, 로그 없는 구간 약 50ms)과 14:00 실행(밖 약 42, 안 64ms, 같은 구간 약 30ms)은 총 시간은 비슷했지만 배분이 달랐다. 두 실행의 값을 한 실행의 추정으로 합치지 않는다.
- 클래스 로드 시간을 직접 재는 방법, JIT·스레드 생성 같은 다른 후보를 가려내는 방법을 아직 정하지 못했다.
- `health`가 첫 요청일 때 필터 밖이 더 길었던 이유를 확인해야 한다. 값이 14:24 한 묶음(2회)뿐이라 다시 재야 한다.
- 스레드가 요청마다 바뀌는 이유(부록 B)와, 톰캣의 대기 줄 3종(스레드 수 `threads.max`, 동시 연결 수 `max-connections`, 연결 대기 큐 `accept-count`의 상한)이 각각 어떤 줄인지 아직 공부하지 못했다. → Q2를 이어서 진행한다.
- `connectionTimeout=30000`이 DB를 내렸을 때 실제로 30초 대기로 나타나는지는 실험하지 않았다. DAY 001의 미확인 항목은 그대로 남아 있다.
- 측정하다 겪은 일: 13:41 실행에서 서버 로그를 파일로 보내는 `tee`(출력을 화면과 파일에 동시에 보내는 명령) 두 개가 같은 파일을 열어 파일이 깨졌고, 그 실행의 서버 시간 로그를 잃었다. → 실행마다 로그 파일명을 새로 쓴다.

결론은 이 환경에서 "이렇게 관찰됐다"까지다. 표본이 적어서(필터 로그가 있는 재기동 실행 9회, 클래스 로딩 실험 1회) 다른 환경에서도 같다고 말할 수는 없다.

## 측정 상세 (부록)

### A. 실행별 요청 시간

괄호 안은 curl total, 단위는 ms이다. 순서는 `첫 요청 → 두 번째 요청`이다. 표는 시각순이 아니라 첫 요청 경로별로 묶었다(`health`를 먼저 보낸 실행, `liveness`를 먼저 보낸 실행). `–`는 curl 값이 없거나(13:20, 13:23, 13:35) 로그를 잃어서(13:41) 계산하지 못한 칸이다.

실험 의도: 14:24의 두 실행은 `health`를 먼저 보냈을 때 `liveness`가 빠른지, 16:27의 두 실행은 `health` 없이도 두 번째 `liveness`가 빠른지를 보려고 했다.

| 실행 | 순서 | 첫 요청: 필터 안 (curl) | 첫 요청: 필터 밖 | 두 번째 요청: 필터 안 (curl) |
|---|---|---|---|---|
| 13:20 | health → health | 62 | – | 3 |
| 13:23 | health → health | 61 | – | 3 |
| 13:35 | health → health | 63 | – | 3 |
| 14:24 #1 | health → liveness | 84 (159.7) | 약 76 | 4 (7.0) |
| 14:24 #2 | health → liveness | 63 (146.5) | 약 84 | 6 (9.9) |
| 13:41 | liveness → health | 로그 유실 (106.5) | – | 로그 유실 (13.3) |
| 13:43 | liveness → health | 49 (110.2) | 약 61 | 11 (13.2) |
| 14:00 (클래스 로딩 로그 켬) | liveness → health | 64 (105.5) | 약 42 | 16 (17.9) |
| 16:27 #1 | liveness → liveness | 69 (124.3) | 약 55 | 3 (6.3) |
| 16:27 #2 | liveness → liveness | 60 (109.9) | 약 50 | 4 (8.5) |

- 13:23 실행에서 같은 앱에 `health`를 10번 더 보냈다. 앱 기준 세 번째 요청은 필터 안 19ms(curl 29.7)였고 이후 2~5ms였다. 세 번째 요청이 올라간 이유는 확인하지 못했다.
- 필터 로그가 있는 실행은 9회이고 로그를 잃은 실행이 1회(13:41)다. 첫 요청 경로(`health`/`liveness`)별 실행을 번갈아 하지 않아, 경로의 영향과 실행 시점에 따른 우연한 차이를 구분하지 못했다.
- 필터 안 49~69ms(`liveness` 첫 요청 4회)에는 클래스 로딩 로그를 켠 14:00 실행의 64ms가 들어 있다. 이를 빼도 범위는 49~69ms다.

### B. HikariCP (13:35 실행)

`application.yml`에 `logging.level.com.zaxxer.hikari: DEBUG`를 넣어 읽었다(필요할 때만 켜고 커밋하지 않았다). `connection-adder`는 HikariCP가 커넥션을 채우는 백그라운드 스레드의 이름이다.

| 항목 | 값 |
|---|---|
| `maximumPoolSize` / `minimumIdle`(놀고 있는 커넥션을 최소 몇 개 유지할지) | 10 / 10 |
| `connectionTimeout` | 30000ms |
| 첫 커넥션 확립 | 약 166ms (시도 26.744 → 확립 26.910) |
| 이후 커넥션: 시도와 시도 사이 간격(8회) | 약 40~61ms |
| 이후 커넥션: 확립에 걸린 시간 | 약 9~26ms |
| `Start completed`(시작 완료 로그, `total=1/10`은 풀에 커넥션이 1개 있다는 뜻) → 풀 10/10 완성 | 약 0.5초 (538ms) |
| 풀 10/10 완성 → 첫 요청 | 약 7초 |

첫 1개는 앱이 뜨는 중에 `main` 스레드가 만들고, 나머지는 `connection-adder`가 순차로 채웠다. 9개를 채우는 데 538ms가 걸렸고, 시도 간격(8회, 40~61ms)과 마지막 확립(9~26ms)을 더하면 329~514ms다(8×40+9, 8×61+26). 538ms에서 514ms를 뺀 **24ms 이상은 설명하지 못했다.** 간격이 생기는 이유도 확인하지 못했다. 13:43 실행에서는 풀 상태를 직접 보지 않았다.

같은 13:35 실행에서 보낸 10개 요청(첫 요청 63ms 포함)의 처리 스레드는 `exec-1, 2, 4, 6, 8, 10, 2, 4, 6, 8`이었다. 요청을 하나씩 보냈는데도 처리한 스레드가 바뀐 이유는 확인하지 못했다.

### C. 클래스 로딩 실험의 보정과 상세 (14:00 실행)

요청 전송 시각을 `curl` 실행 직전에 찍었더니 실제보다 약 12ms 일찍 기록됐다. 그래서 전송 시각을 `필터 끝 + 응답쓰기(약 1ms, 가정) − curl total`로 역산해 보정하고, 이 시각으로 구간 길이를 다시 계산했다. 역산한 값이므로 구간 합(30 + 10 + 64 ≈ 104ms)이 curl 105ms와 맞는 것은 검증이 아니다. 30ms·10ms 소구간은 역산 경계에 의존하는 참고값이다.

| 구간 | 길이 | 새로 로드된 클래스 | 주로 로드된 것 |
|---|---|---|---|
| 유휴 (기동 완료 ~ 첫 요청 전송) | 약 5.7초 | 255개 (전부 기동 직후 1초 안) | JVM 모니터링 기능(JFR·JMX: JVM 내부 상태를 기록·노출), 메트릭 수집(micrometer) |
| 첫 요청 전송 ~ 서블릿 초기화 시작 | 약 30ms | **139개** | `tomcat` 51, `coyote` 29(연결·프로토콜 처리), `catalina` 21(서블릿 컨테이너) |
| 서블릿 초기화 시작 ~ 필터 시작 | 약 10ms | 46개 | micrometer, catalina |
| 필터 안 | 64ms | **328개** | `jackson.databind` 114(JSON 변환), `springframework.web` 66(스프링 웹 모듈) |
| 첫 요청 끝 ~ 두 번째 요청 전송 | 약 1초 | 4개 | |
| 두 번째 요청(`health`) | 약 17ms | 27개 | `java.lang.invoke`(JVM의 메서드 호출 기능), `springframework.jdbc` 5, `transaction` 3 |

13:43 실행의 타임라인(§3)에서 서블릿 초기화(44.250)가 필터 시작(44.260)보다 앞선다. 톰캣은 첫 요청에서 서블릿을 먼저 준비한 뒤 필터 체인을 만들어 실행한다고 알고 있고, 이번 로그의 순서가 이와 일치한다(이번 실험으로 따로 확인한 것은 아니다). 또 로그의 `1 ms`와 시각 차 2ms의 차이는 로그의 밀리초 절삭 때문으로 보인다.
