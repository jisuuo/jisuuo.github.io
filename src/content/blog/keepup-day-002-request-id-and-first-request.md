> 일정표상 DAY 002는 10/11이지만, 1주차 산출물이 DAY 001에 끝나 로드맵 2주차의 측정 기반을 하루 앞당겨 10/10에 진행했다.

**이 글에서 쓰는 말**
- **태그**: `[직접 관찰]`은 로그·측정에서 직접 읽은 값, `[계산한 추정]`은 측정값에서 계산한 값, `[설정 의미 정리]`는 이번 실험으로 확인하지 않은 일반적인 동작이다.
- **Q2**: 이 시리즈의 체크리스트 질문 2번 "서버 안에서 누가 처리하지?"(스레드·커넥션 풀).
- **MDC**: 현재 스레드에 붙는 key-value 보관함. 로그 패턴에서 꺼내 쓴다.
- **필터(Filter)**: 서블릿 컨테이너가 요청을 받자마자 거치는 처리 단계.
- **실행**: 앱을 새로 재기동한 한 번. 시각으로 부른다(13:43 실행).
- **`liveness` / `health`**: `/actuator/health/liveness`는 DB 확인이 없고, `/actuator/health`는 DB 연결 확인을 포함해 여러 항목을 함께 확인한다(`[설정 의미 정리]`).
- **예측**: 실험 전에 내가 적어 둔 값(§4).
- **클래스 로드**: JVM이 처음 쓰는 클래스를 메모리에 올리는 일.
- **유휴**: 앱은 떠 있지만 요청이 없는 상태.
- **curl total**: `curl`이 요청을 보내고 응답을 다 받을 때까지의 시간(`time_total`).
- **필터 안**: 우리 필터(`RequestLogFilter`)가 잰 시간.
- **필터 밖**: curl total에서 필터 안을 뺀 나머지. 연결과 필터 시작 전 구간, 응답을 쓰고 받는 시간이 모두 들어간다.

**요약**
1. **`liveness` 3ms 예측은 틀렸다.** "첫 요청이 느린 건 DB 확인 때문"이라고 봤지만, DB 확인이 없는 `liveness`도 첫 요청일 때 느렸다(필터 안 49~69ms). 첫 요청의 필터 안 시간은 `health`와 `liveness`가 비슷했다(중앙값 63ms 대 62ms). 두 번째 요청은 `liveness`가 앞이 무엇이든 3~6ms였고, `health`는 앞이 `liveness`일 때 11~16ms였다(§3-1).
2. **관찰된 것.** 첫 요청에서 처음 쓰는 클래스가 대량으로 로드됐다(14:00 실행 1회: 첫 요청 513개, 두 번째 요청 27개). 이것이 첫 요청 지연의 유력한 후보다.
3. **하지 않은 것·못 잰 것.** Q2의 원래 질문(DB를 내렸을 때 누가 요청을 붙잡나)은 로드맵 2주차 항목("풀 기본값 확인") 범위 밖이라 하지 않았고, 클래스 로드에 걸린 시간은 재지 못했다.

## 1. 오늘의 목표
- 모든 요청에 requestId를 붙이고, 요청별 `상태 코드 + 걸린 시간`을 로그 한 줄로 남기는 필터를 만든다.
- 오늘의 질문(Q2): DB를 내려둔 동안 응답이 오래 걸렸다면, 요청을 붙잡고 있던 건 누구(어느 스레드·어느 풀)인가. 로드맵의 2주차 항목은 "풀 기본값 확인"까지여서, 오늘은 HikariCP(JDBC 커넥션 풀 라이브러리) 기본값과 측정 기반까지만 봤고 DB를 내리는 실험은 하지 않았다.

## 2. 따라간 요청

**필터가 남기는 것**

요청마다 8자리 requestId를 만들어 MDC에 넣고, 응답 헤더 `X-Request-Id`로도 돌려준다. 요청이 끝나면 한 줄을 남기고 MDC를 비운다(커밋 `03e3895`, 발췌이며 일부 줄을 단순화했다).

```java
MDC.put("requestId", requestId);
response.setHeader("X-Request-Id", requestId);
long start = System.nanoTime();
try {
    chain.doFilter(request, response);
} finally {
    long elapsedMs = (System.nanoTime() - start) / 1_000_000;
    log.info("{} {} -> {} {}ms", method, uri, response.getStatus(), elapsedMs);
    MDC.remove("requestId");
}
```

실제로 찍힌 로그 한 줄(13:43 실행, 포트는 8080이 사용 중이어서 8081). `exec-N`은 톰캣 워커 스레드 이름이다.

```
13:43:44.309 [http-nio-8081-exec-1] [2c12f355] INFO  ...RequestLogFilter - GET /actuator/health/liveness -> 200 49ms
```

**따라간 요청**

13:43 실행에서 재기동 직후 보낸 첫 요청 `GET /actuator/health/liveness` 1건이다.

```
13:43:44.200  curl이 요청을 보냄          ← 추정: 44.309 + 응답쓰기(약 1ms, 가정) − 110ms로 역산
   ↓ 약 50ms   (이 구간에는 로그가 없음)
13:43:44.250  DispatcherServlet 초기화 시작   (스프링 MVC의 요청 진입점 서블릿)
13:43:44.252  초기화 끝 (로그: 1 ms, 시각 차 2ms는 로그의 밀리초 절삭 때문으로 보임)
   ↓ 약 8ms
13:43:44.260  RequestLogFilter 시작      ← 추정: 44.309 − 49ms
13:43:44.309  RequestLogFilter 끝, 49ms 기록
              curl total = 110.2ms
```

| 구간 | 소요 | 구하는 법 |
|---|---|---|
| 필터 안 | 49ms | 서버 로그 |
| 필터 밖 | 약 61ms | 110.2 − 49 (정수 ms 버림 때문에 ±수 ms 오차) |
| 전체 | 110.2ms | curl total |

같은 실행의 두 번째 요청(`health`)은 curl 13.2ms, 필터 안 11ms, 필터 밖 약 2ms였다.

서블릿 초기화(44.250)가 필터 시작(44.260)보다 앞선다. `[설정 의미 정리]` 톰캣은 첫 요청에서 서블릿을 먼저 준비한 뒤 필터 체인을 만들어 실행한다고 알고 있고, 이번 로그의 순서가 이와 일치한다. 이번 실험으로 따로 확인한 것은 아니다.

## 3. 측정값

**3-1. 실행별 요청 시간**

괄호 안은 curl total, 단위는 ms이다. 순서는 `첫 요청 → 두 번째 요청`이다. 표는 시각순이 아니라 첫 요청 경로별로 묶었다(`health`를 먼저 보낸 실행, `liveness`를 먼저 보낸 실행). `–`는 curl 값이 없거나(13:20, 13:23, 13:35) 로그를 잃어서(13:41) 계산하지 못한 칸이다. 13:23 실행의 세 번째 요청 curl 값은 아래 불릿에 있다.

실험 의도: 14:24의 두 실행은 `health`를 먼저 보냈을 때 `liveness`가 빠른지, 16:27의 두 실행은 `health` 없이도 두 번째 `liveness`가 빠른지를 보려고 했다.

| 실행 | 순서 | 첫 요청: 필터 안 (curl) | 첫 요청: 필터 밖 | 두 번째 요청: 필터 안 (curl) |
|---|---|---|---|---|
| 13:20 | health → health | 62 | – | 3 |
| 13:23 | health → health | 61 | – | 3 |
| 13:35 | health → health | 63 | – | 3 |
| 14:24 #1 | health → liveness | 84 (159.7) | 약 76 | 4 (7.0) |
| 14:24 #2 | health → liveness | 63 (146.5) | 약 84 | 6 (9.9) |
| 13:41 | liveness → health | 로그 유실 (106.5) | – | 로그 유실 (13.3) |
| 13:43 | liveness → health | 49 (110.2) | 약 61 | 11 (13.2) |
| 14:00 (클래스 로딩 로그 켬) | liveness → health | 64 (105.5) | 약 42 | 16 (17.9) |
| 16:27 #1 | liveness → liveness | 69 (124.3) | 약 55 | 3 (6.3) |
| 16:27 #2 | liveness → liveness | 60 (109.9) | 약 50 | 4 (8.5) |

- 첫 요청의 필터 안은 `health`가 61~84ms(5회, 중앙값 63), `liveness`가 49~69ms(4회, 중앙값 62)로 비슷했다. 클래스 로딩 로그를 켠 14:00 실행의 64ms를 빼도 `liveness` 범위는 49~69ms다.
- 첫 요청의 curl total은 `health`가 146.5~159.7ms(2회), `liveness`가 105.5~124.3ms(5회)였다. 첫 요청의 필터 밖은 `health`가 약 76~84(2회), `liveness`가 약 42~61(4회)로 `health`가 더 컸다. `health`의 이 값들은 모두 14:24 한 묶음에서 나왔다.
- 이 차이는 필터 밖에 있다. DB 확인은 필터 안쪽에서 실행되므로 이 차이는 DB 확인으로는 설명되지 않고, 이유는 확인하지 못했다.
- 두 번째 요청의 필터 안은 `liveness`가 3~6ms(4회: 앞이 `liveness`일 때 3~4, 앞이 `health`일 때 4~6)였다. 앞의 요청 종류와 상관없이 빨랐으므로, 첫 요청이라는 조건의 효과가 크다고 보인다.
- 두 번째 `health`는 앞이 `liveness`면 필터 안 11~16ms(2회), 앞이 `health`면 3ms(3회)였다. 처음 쓰는 `health`가 두 번째 `liveness`보다 안쪽 시간이 약 5~13ms 길었다(표본 2회).
- 13:23 실행에서 같은 앱에 `health`를 10번 더 보냈다. 앱 기준 세 번째 요청은 필터 안 19ms(curl 29.7)였고 이후 2~5ms였다. 세 번째 요청이 올라간 이유는 확인하지 못했다.
- 필터 로그가 있는 실행은 9회이고 로그를 잃은 실행이 1회(13:41)다. 첫 요청 경로(`health`/`liveness`)별 실행을 번갈아 하지 않아, 경로의 영향과 실행 시점에 따른 우연한 차이를 구분하지 못했다.

**3-2. HikariCP (13:35 실행)**

로그 설정: `application.yml`에 `logging.level.com.zaxxer.hikari: DEBUG`를 넣어 읽었다(필요할 때만 켜고 커밋하지 않았다).

| 항목 | 값 |
|---|---|
| `maximumPoolSize` / `minimumIdle`(놀고 있는 커넥션을 최소 몇 개 유지할지) | 10 / 10 |
| `connectionTimeout` | 30000ms |
| 첫 커넥션 확립 | 약 166ms (시도 26.744 → 확립 26.910) |
| 이후 커넥션: 시도와 시도 사이 간격(8회) | 약 40~61ms |
| 이후 커넥션: 확립에 걸린 시간 | 약 9~26ms |
| `Start completed`(HikariCP 시작 완료 로그, `total=1/10`은 풀에 커넥션이 1개 있다는 뜻) → 풀 10/10 완성 | 약 0.5초 (538ms) |
| 풀 10/10 완성 → 첫 요청 | 약 7초 |

첫 1개는 앱이 뜨는 중에 `main` 스레드가 만들고, 나머지는 `connection-adder`(HikariCP의 백그라운드 채움 스레드)가 순차로 채웠다.

9개를 채우는 데 538ms가 걸렸다. 시도 간격(8회, 40~61ms)과 마지막 확립(9~26ms)을 더하면 329~514ms다(8×40+9, 8×61+26). 538ms에서 514ms를 뺀 **24ms 이상은 설명하지 못했다.**

같은 13:35 실행에서 보낸 10개 요청(첫 요청 63ms 포함)의 처리 스레드는 `exec-1, 2, 4, 6, 8, 10, 2, 4, 6, 8`이었다. 요청을 하나씩 보냈는데도 처리한 스레드가 바뀐 이유는 확인하지 못했다(§5).

**3-3. 클래스 로딩 실험 (14:00 실행)**

`java -jar`에 `-Xlog:class+load:file=<파일>:time,uptime` 옵션(클래스가 로드될 때마다 시각을 기록)을 켜고, 재기동 후 `liveness` → `health`를 1회씩 보냈다(첫 요청 curl 105ms·필터 안 64ms, 두 번째 curl 17.9ms·필터 안 16ms).

요청 전송 시각을 `curl` 실행 직전에 찍었더니 실제보다 약 12ms 일찍 기록됐다. 그래서 전송 시각을 `필터 끝 + 응답쓰기(약 1ms, 가정) − curl total`로 역산해 보정하고, 이 시각으로 구간 길이를 다시 계산했다. 역산한 값이므로 구간 합(30 + 10 + 64 ≈ 104ms)이 curl 105ms와 맞는 것은 검증이 아니다. 30ms·10ms 소구간은 역산 경계에 의존하는 참고값이다.

| 구간 | 길이 | 새로 로드된 클래스 | 주로 로드된 것 |
|---|---|---|---|
| 유휴 (기동 완료 ~ 첫 요청 전송) | 약 5.7초 | 255개 (전부 기동 직후 1초 안) | JVM 모니터링 기능(JFR·JMX: JVM 내부 상태를 기록·노출), 메트릭 수집(micrometer) |
| 첫 요청 전송 ~ 서블릿 초기화 시작 | 약 30ms | **139개** | `tomcat` 51, `coyote` 29(연결·프로토콜 처리), `catalina` 21(서블릿 컨테이너) |
| 서블릿 초기화 시작 ~ 필터 시작 | 약 10ms | 46개 | micrometer, catalina |
| 필터 안 | 64ms | **328개** | `jackson.databind` 114(JSON 변환), `springframework.web` 66(스프링 웹 모듈) |
| 첫 요청 끝 ~ 두 번째 요청 전송 | 약 1초 | 4개 | |
| 두 번째 요청(`health`) | 약 17ms | 27개 | `java.lang.invoke`(JVM의 메서드 호출 기능), `springframework.jdbc` 5, `transaction` 3 |

첫 요청에서 로드된 클래스는 필터 전 185개(139 + 46), 필터 안 328개, 합계 513개다.

비교 기준은 유휴 구간이다. 유휴 255개는 전부 기동 직후 1초 안에 로드됐고, 첫 요청 직전 2초 동안은 0개였다. 평소 기준이 0에 가까운데, 첫 요청 전 약 30ms 동안 139개가 로드됐다.

한계:
- 개수를 센 것이지 로드에 걸린 시간을 잰 것이 아니다. 개수는 처음 실행된 코드의 양을 간접으로 보여 줄 뿐이다.
- JIT 컴파일(자주 실행되는 코드를 실행 중에 최적화해 컴파일하는 JVM 기능), 스레드 생성 등 다른 "처음 한 번만" 후보는 배제하지 못했다.
- 클래스 로딩 로그와 `java -jar` 실행이 시간에 영향을 줬을 수 있다. 다만 이 실행의 첫 요청 필터 안 64ms는 다른 실행의 범위(49~84ms) 안이다.
- 구간 경계는 시각에서 계산한 추정이고, 표본은 1회이다.

## 4. 배운 것: 한 층 아래

**요청이 거치는 층**
- `[설정 의미 정리]` 필터는 DispatcherServlet 앞에서 걸린다. 그래서 모든 요청의 입구·출구를 한 곳에서 감싸기에 맞다. 인터셉터는 스프링 MVC가 요청을 처리할 핸들러(컨트롤러 메서드)를 정한 뒤에야 그 호출 전후에 걸린다.
- `[설정 의미 정리]` 필터에서 MDC에 `requestId`를 넣으면 같은 스레드의 모든 로그 줄에 `%X{requestId}`로 찍힌다. 톰캣은 스레드를 재사용하므로 `finally`에서 지워야 한다.
- `[계산한 추정]` 13:43 실행의 첫 요청에서는 필터 밖(약 61ms)과 안(49ms)이 두 번째 요청(안 11ms, 밖 약 2ms)보다 모두 컸고, 밖이 조금 더 길었다.

**풀에 대해 확인한 것**
- `[직접 관찰]` 13:35 실행에서 첫 요청이 올 때 풀은 이미 10/10이었다.

**내 예측과 결과**
- 예측: `liveness` 약 3ms, `health` 약 63ms (첫 요청이 느린 건 DB 확인 때문이라고 봄). 순서 실험(13:41)을 하기 직전에 적었다. 이 시점에는 `health`가 첫 요청일 때 61~63ms가 나온 실행이 이미 세 번(13:20, 13:23, 13:35) 있었다.
- 결과: §3-1 표와 같다. `liveness` 3ms는 틀렸다. `health` 63ms는 앞선 세 번의 관찰값을 이어 적은 것이라 맞았다.
- 말할 수 있는 것: DB **커넥션 생성**은 첫 요청 지연의 주된 원인으로 보이지 않는다. 13:35 실행에서 풀은 첫 요청 7초 전에 이미 10/10이었다. DB 확인이 없는 `liveness`로도 같은 지연이 나타난 근거는 §3-1의 `liveness` 실행들이다.
- 말할 수 없는 것: DB **확인**의 몫이 0이라는 것. 첫 요청의 필터 안은 `health`와 `liveness`가 비슷했지만, 두 번째 요청에서는 처음 쓰는 `health`가 안쪽 시간이 약 5~13ms 더 길었다(§3-1).

**어디까지 말할 수 있나:** 클래스가 대량으로 로드됐다는 것은 관찰됐다. 그것이 지연의 원인이라는 것은 유력한 후보다. 시간을 재지 않았으므로 확정은 아니다(§3-3).

**내가 배운 것:** 요청 시간을 분석할 때 추측하고 넘어가지 않고, 먼저 측정 도구(필터 로그)를 만들어 수치로 판단하려고 했다. "첫 요청이 느린 건 DB 확인 때문"이라는 추측은 `liveness`를 첫 요청으로 보내도 느렸고 두 번째로 보내면 빨랐다는 결과로, 주된 원인이 아닌 것으로 보였다. 필터 전 구간에는 로그가 없어서, 클래스 로딩 로그를 켜고 그 구간에서 클래스가 몇 개 로드되는지 세어, 가설과 일치하는 관찰을 얻었다.

## 5. 막힌 것 / 다음에 볼 것
- **필터에 닿기 전 약 50ms 동안 서버가 무엇을 하는지** 로그에는 없다(13:43 실행, §2).
  - **내 가설:** 이 구간은 톰캣이 첫 요청에서 처음 쓰는 클래스를 로드하는 시간일 것이다.
  - **근거:** 별도 실행인 14:00 실행의 클래스 로딩 로그(§3-3)에서, 요청 전송부터 서블릿 초기화 시작까지 약 30ms 동안 139개가 새로 로드됐다(필터 전 전체로는 185개). 두 번째 요청은 27개였다. 가설과 일치하는 관찰이지만, 로드에 걸린 시간은 재지 않았으므로 원인으로 확정하지는 않는다.
  - **실행 간 차이:** 13:43 실행(필터 밖 약 61, 안 49ms, 로그 없는 구간 약 50ms)과 14:00 실행(밖 약 42, 안 64ms, 같은 구간 약 30ms)은 총 시간은 비슷했지만 배분이 달랐다. 두 실행의 값을 한 실행의 추정으로 합치지 않는다.
- 클래스 로드 시간을 직접 재는 방법, JIT·스레드 생성 같은 다른 후보를 가려내는 방법을 아직 정하지 못했다.
- `health`가 첫 요청일 때 필터 밖이 더 길었던 이유를 확인해야 한다. DB 확인은 필터 안쪽에서 실행되므로 다른 원인일 수 있고, 값이 14:24 한 묶음(2회)뿐이라 다시 재야 한다.
- 스레드가 요청마다 바뀌는 이유(§3-2)와, 톰캣의 대기 줄 3종(스레드 수 `threads.max`, 동시 연결 수 `max-connections`, 연결 대기 큐 `accept-count`의 상한)이 각각 어떤 줄인지 아직 공부하지 못했다. → Q2를 이어서 진행.
- `connectionTimeout=30000`이 DB를 내렸을 때 실제로 30초 대기로 나타나는지는 실험하지 않았다. DAY 001의 미확인 항목은 그대로 남아 있다.
- 표본 수와 한계는 §3-1, §3-3에 있다. 결론은 이 환경에서 "이렇게 관찰됐다"까지다.
- 13:41 실행에서 서버 로그를 파일로 보내는 `tee`(출력을 화면과 파일에 동시에 보내는 명령) 두 개가 같은 파일을 열어 파일이 깨졌고, 그 실행의 서버 시간 로그를 잃었다. → 실행마다 로그 파일명을 새로 쓴다.
