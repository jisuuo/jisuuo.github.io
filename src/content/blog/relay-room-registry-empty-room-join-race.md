방에 남은 마지막 1명이 나가면서 빈 방을 지우는 순간 다른 세션의 입장이 끼어들면, 그 세션은 **이미 지워진 방에 들어간다.** 입장은 성공한 것처럼 보이고 예외도 없다. 그 뒤로 그 방의 메시지를 받지 못할 뿐이다. 이 글은 이 문제를 테스트로 재현하고 락으로 막은 기록이다.

결론부터 말하면 방 관리자 전체에 락 하나를 거는 방식(전체 락)을 택했다. "방마다 락 + 재확인"도 구현해 로컬에서 비교했지만 빨랐던 조건이 좁았고 다른 대가가 확인돼 바꾸지 않았다. 실제 부하 측정에서 락 대기가 병목으로 확인되면 다시 검토한다.

Relay는 Java 21, Spring Boot 4.1.2, Raw WebSocket으로 만드는 학습용 채팅 서버이고, 이 글은 시리즈 세 번째로 Phase 1의 과제 P1-3(채팅방 및 세션 관리)을 다룬다. AI(Claude)가 질문·힌트·반례를 던지고 사용자가 먼저 답했다. 코드·테스트·문서는 사용자가 요청한 뒤 AI가 작성했다. 사용자가 했다고 밝힌 따옴표 문장과 인용 블록은 원문 그대로이고, 그 밖의 따옴표는 기록 문서의 문구다.

## 두 매핑과 불변식은 어떻게 정했나

P1-2에서 한 세션이 여러 방에 들어갈 수 있게 정했기 때문에, 방 관리자(`RoomRegistry`)는 방 → 세션들 매핑과 세션 → 방들 매핑을 함께 가진다. 두 번째 매핑은 끊김 정리용이다. 방 → 세션들 매핑만 있으면 끊긴 세션(`WebSocketSession`) 하나를 찾으려고 전체 방을 훑어야 한다(정의 단계의 예시: 방이 10,000개면 그 세션이 든 방이 2개뿐이어도 전부 훑는다). 사용자는 보통 퇴장(`LEAVE`) 없이 연결을 끊으므로 이 정리가 주요 경로다.

정의 단계에서는 "문제 찾기 질문 6개"를 썼다. 1번 질문 "항상 참이어야 하는 문장은?"에 사용자가 적은 문장이 불변식이 됐다.

1. S ∈ 방 A의 세션들 ⇔ A ∈ S의 방들 (사용자가 적은 "방 A에 S가 있으면 S의 방 목록에도 A가 있다", "방 A에 S가 없으면 S의 방 목록에도 A가 없다"를 합친 것)
2. 빈 방은 존재하지 않는다
3. 끊긴 세션은 매핑에 없다

정의 기록에는 퇴장 때는 할 일이 없고 끊김 때는 재연결에 대비해 그대로 둔다는 처음 생각이 고칠 대상으로 남아 있다. 둘 다 위 불변식을 깨뜨린다. 끊긴 세션은 다시 쓸 수 없고, 다시 접속하면 새 세션이 생긴다. 기록(plan)에는 끊김 처리에서 빈 방과 빈 세션 항목을 빈 값으로 남긴다고 처음 답했다가, 사용자가 적은 ②·③에 비춰 없애야 한다로 고쳤다고 정리돼 있다. 남겨 두면 끊김마다 빈 항목이 쌓여 메모리 누수가 된다.

## 문제 문장을 반례로 다듬기

2번 질문 "누가 동시에 건드리나?"에 사용자의 처음 답은 "잘 모르겠다"였다. 그래서 동시 실행 순서를 표로 따라갔다.

| 시점 | 스레드 1 (S `LEAVE A`) | 스레드 2 (T `JOIN A`) | 방 → 세션들 매핑 | 스레드 2가 쥔 집합 |
|---|---|---|---|---|
| 1 | 방 A에서 S 제거 | | `{A → {}}` | — |
| 2 | "비었네" 확인 | | `{A → {}}` | — |
| 3 | | 방 A 집합을 꺼내 쥠 | `{A → {}}` | `{}` |
| 4 | 방 → 세션들 매핑에서 방 A 삭제 | | `{}` | `{}` (매핑과 연결 끊김) |
| 5 | | 쥔 집합에 T 추가, 세션 → 방들 매핑의 T 항목에 A 추가 | `{}` | `{T}` |

표를 따라간 사용자가 찾은 결과는 "맵에서 A는 사라지고 T 방 목록엔 A가 남아 ① 깨짐"이었다. `ConcurrentHashMap`의 `get`·`remove`·`add` 하나하나는 안전하다. 깨지는 것은 "빈 방 확인 → 삭제", "방 찾기 → 추가"처럼 **여러 단계를 묶은 동작**이고, 단계 사이의 틈에 다른 스레드가 끼어든다.

사용자의 처음 문제 문장은 "JOIN과 LEAVE가 동시에 일어나면 방 목록 불일치로 메시지 유실"이었다. AI가 반례를 냈다. 방에 2명이면 한 명이 나가도 방이 삭제되지 않으니 문제가 없다. 사용자가 조건을 좁혀 다시 적은 문장은 이렇다.

> "마지막 1명 LEAVE로 빈 방 삭제 직전 JOIN이 방을 쥐면 유실"

끊김 처리에도 같은 경쟁이 생기느냐는 질문에 사용자는 "생깁니다. 따로 그 부분에 대한 방어 조치를 안했기 때문입니다."라고 답했다. AI는 구조적 이유를 보충했다. 끊김 처리(`removeSession`)에도 같은 "빈 방 확인 → 삭제" 2단계가 있으니, 문제는 퇴장이나 끊김이 아니라 빈 방 삭제 동작 자체에 있다.

## 재현: 방어 없는 구현에서 먼저 실패시키기

5번 질문 "그게 지켜지는지 어떻게 확인하지?"에 사용자는 "스레드 여러 개로 동시에 LEAVE·JOIN, 여러 번 반복"이라고 답했다. 깨지는 틈(방을 꺼낸 뒤·추가하기 전)이 좁아서 경쟁 테스트(`RoomRegistryConcurrencyTest`)는 이렇게 짜였다.

- 시도마다 방 1,000개에 세션을 1명씩 넣는다.
- 두 스레드를 출발선에 세웠다가 `CountDownLatch`(출발 신호)로 같은 순간에 출발시킨다. 한 스레드는 모든 방에서 그 1명을 퇴장(또는 끊김) 처리하고, 다른 스레드는 같은 방들에 새 세션을 입장시킨다.
- 끝나면 불변식 ①·②를 양방향으로 검사하고, 이를 200번 반복한다.

양방향이어야 하는 이유는 이 경쟁에서는 방 → 세션들 매핑에 방 자체가 없어 그 방향으로는 검사할 것이 없고, 세션 → 방들 매핑 쪽에서 훑어야만 드러나기 때문이다.

테스트가 문제를 잡는지 보려고 먼저 방어 없는 `ConcurrentHashMap` 구현에서 돌렸다.

- **11회 실행 모두 두 테스트 실패.** 테스트별로 나눠 확인한 5회에서 200회 시도 중 위반이 생긴 시도는 퇴장 경로 22~36회, 끊김 경로 20~45회였다.
- 위반은 모두 "세션 목록에는 방 A가 있는데 맵에 방 A(또는 그 안의 세션)가 없음"이었다. 즉 세션 → 방들 매핑에는 A가 있는데 방 → 세션들 매핑에는 A(또는 그 안의 세션)가 없다. 실행 전 예상과 같은 방향이다. **예외는 없었다.**

테스트는 그대로 두고 구현만 바꿔 방 관리자의 모든 메서드를 `synchronized`(락 하나)로 감쌌다. 결과는 **같은 테스트 5회 모두 통과**였다. 핸들러 연결 전 실패하던 통합 테스트 2개도 연결 후 통과해 `./gradlew test` 전체 42개가 통과했다. 다만 통과는 "이 조건에서 겹침을 찾지 못했다"는 뜻이지 안전 증명이 아니다. 안전하다는 근거는 모든 접근이 같은 락 안에 있다는 추론이다.

## 왜 방마다 락은 안 되고, 재확인은 무엇을 확인하나

고민 단계에서 사용자가 처음 고른 방식은 **방마다 락**(락 객체는 방마다 존재)이었다. AI가 낸 반례 타임라인을 사용자가 따라가 같은 문제를 확인했다.

1. 스레드 2가 방 A를 꺼내 그 방의 락을 기다린다.
2. 스레드 1이 락 안에서 S를 제거하고 방 → 세션들 매핑에서 방 A를 삭제한 뒤 락을 푼다.
3. 스레드 2가 락을 잡고, 이미 삭제된 방에 T를 추가한다.

락은 락 안의 동작끼리만 막는다. 방마다 락에서는 "방 찾기"가 락 바깥, "추가"만 락 안에 있다. 방을 찾기 전에 잡을 수 있는 락은 방 락이 아니라 방 → 세션들 매핑 쪽 락, 즉 전체 락이 된다.

방마다 락을 살리는 대안이 **방마다 락 + 재확인**이다. 락을 잡은 뒤 확인하는 대상은 방 A가 있는지가 아니라, 방 → 세션들 매핑에 있는 방 A가 내가 쥔 바로 그 객체인지다. 그사이 다른 입장이 같은 이름의 새 방을 만들 수 있기 때문이다. 다르면 처음부터 다시 한다. 아래는 비교 실험용으로 만든 `PerRoomLockRoomRegistry`(실험용 테스트 코드)의 `join` 원문이다.

```java
	boolean join(WebSocketSession session, String roomId) {
		while (true) {
			Room room = rooms.computeIfAbsent(roomId, id -> new Room());
			synchronized (room) {
				if (rooms.get(roomId) != room) {
					retries.increment();
					continue;
				}
				boolean added = room.members.add(session);
				roomsBySession.compute(session, (s, joined) -> {
					Set<String> result = joined == null ? new HashSet<>() : joined;
					result.add(roomId);
					return result;
				});
				return added;
			}
		}
	}
```

`rooms.get(roomId) != room`이 이름이 아니라 객체를 비교하는 부분이고, `continue`가 `while (true)`의 처음으로 돌아가 방을 다시 찾는다. 이 "처음부터 다시"를 사용자는 "누군가가 삭제하고 다시 생성하면 그 객체로 들어가기 위한 것. 방을 다시 찾고서 받은 객체로"라고 정리했다. AI는 역할 구분을 보충했다. `computeIfAbsent`는 그 순간의 객체를 돌려줄 뿐이고, 삭제·재생성에 대비하는 것은 락을 잡은 뒤의 참조 비교와 다시 시작이다.

| 대안 | 경쟁을 막는가 | 대가 |
|---|---|---|
| A. 방마다 락 (방 찾기는 락 밖) | 아니오 | — |
| B. 전체 락 하나 | 예 | 서로 다른 방의 작업도 줄을 선다 |
| C. 방마다 락 + 재확인 | 예 | 객체 비교·재시도·락 안 삭제 규칙을 모두 지켜야 한다 |

사용자의 결정은 "전체 락 진행 후 문제 상황 발생 시 방마다 락 + 재확인으로"였다. 줄 서기가 실제 문제인지 아직 재현되지 않았으니 단순한 쪽에서 시작한다.

## EXP-01: 두 방식은 어떤 조건에서 차이가 나는가

결정 뒤 사용자가 "정확히 어떤 요소에서 차이가 나는지도 알아야합니다"라고 요청해 두 방식을 비교했다(EXP-01). 환경은 8코어 노트북 한 대, Java 21.0.11, mock 세션(실제 연결 없는 테스트용 가짜 객체), 실제 I/O 없는 반복 루프다. 스레드마다 입장 → 퇴장을 반복하고, 300ms 예열 뒤 1초를 재서 3회 중 중앙값을 쓴다.

- (가) 스레드마다 다른 방. 혼자라 퇴장할 때마다 방이 삭제되고 다시 만들어진다.
- (가') 스레드마다 다른 방, 상주 세션 1명이 있어 방이 유지된다. 첫 실행에서 (가)의 차이가 예상보다 작게 나와 방 생성·삭제 비용을 떼어 보려고 추가됐다.
- (나) 모든 스레드가 같은 방 하나.

실행 전 사용자의 예상은 이랬다.

> "전체락인 경우 64개의 스레드라면 대기가 생겨 시간이 많이 걸릴 거 같습니다. (가) 서로 다른 방은 락 + 재확인, (나) 같은 방 하나는 두개 별 차이 없을 거 같습니다."

결과((가') 추가 후 2회 실행)는 다음과 같다. 값은 초당 건수이고 입장·퇴장 1회를 각각 1건으로 센다(M은 백만). 비율은 방마다 / 전체다.

| 조건 | 스레드 | 전체 락 (1회 / 2회) | 방마다 락 + 재확인 (1회 / 2회) | 비율 |
|---|---|---|---|---|
| (가) 혼자, 방 삭제·재생성 | 1 | 25.2M / 23.7M | 15.8M / 16.0M | 0.63 / 0.68 |
| | 4 | 12.2M / 12.0M | 7.2M / 7.4M | 0.59 / 0.62 |
| | 16 | 10.6M / 11.5M | 8.9M / 8.7M | 0.84 / 0.76 |
| | 64 | 10.8M / 11.6M | 15.6M / 15.5M | **1.44 / 1.34** |
| (가') 상주 세션, 방 유지 | 1 | 29.5M / 27.6M | 22.3M / 21.1M | 0.76 / 0.77 |
| | 4 | 13.2M / 12.7M | 13.4M / 13.1M | 1.02 / 1.03 |
| | 16 | 12.8M / 13.0M | 20.2M / 20.2M | 1.58 / 1.56 |
| | 64 | 13.0M / 12.7M | 38.5M / 40.7M | **2.97 / 3.20** |
| (나) 같은 방 하나 | 1 | 25.5M / 24.2M | 16.3M / 15.7M | 0.64 / 0.65 |
| | 4 | 13.4M / 13.7M | 9.2M / 9.8M | 0.69 / 0.71 |
| | 16 | 14.5M / 13.9M | 11.9M / 11.7M | 0.82 / 0.84 |
| | 64 | 13.1M / 13.0M | 9.6M / 11.3M | **0.73 / 0.87** |

예상과 맞춰 보면 이렇다.

- 전체 락이 느려진다는 예상: 맞았다. 다만 64개가 아니라 4개부터 이미 1개일 때의 절반 정도였고 그 뒤로는 거의 그대로였다.
- 서로 다른 방은 방마다 락 + 재확인이 빠르다는 예상: 스레드가 많을 때만 맞았다. EXP-01 분석으로는 방이 유지되는 (가')에서만 스레드가 늘수록 앞섰고(64개에서 약 3배), (가)는 64개에서만 1을 넘었다.
- 같은 방은 별 차이 없다는 예상: 방마다 락 + 재확인이 항상 느렸다. EXP-01 분석은 락 하나를 모두 기다리는 것은 같고 재확인·`ConcurrentHashMap`·`compute` 같은 추가 비용만 남기 때문이라고 본다.

정확성은 두 방식 모두 2회 실행 모두 위반 0/200이었다. 이는 실행이 끝난 뒤의 검사다. 실행 도중은 따로 봤다. 스레드 16개가 (가)를 도는 동안 관찰 스레드가 1초 동안 두 매핑의 스냅샷을 반복해서 찍고 불변식을 검사했다. 찍는 방법은 두 구현이 다르다. 전체 락은 같은 락을 잡고 찍고, 방마다 락 + 재확인은 전체를 멈출 락이 없어 두 매핑을 차례로 복사한다.

| 구현 | 찍은 스냅샷 (1회 / 2회) | 불변식 위반 스냅샷 |
|---|---|---|
| 전체 락 | 43,720 / 28,983 | 0 / 0 |
| 방마다 락 + 재확인 | 568 / 243 | 568 / 243 (전부) |

이 위반은 실행 도중의 모습이고, 끝난 뒤 상태(위반 0/200)와는 다르다. EXP-01 분석이 든 이유는 두 가지다. `join`이 락을 잡기 전에 `computeIfAbsent`로 빈 방을 방 → 세션들 매핑에 먼저 넣고, 방 → 세션들 매핑과 세션 → 방들 매핑 갱신 사이에 틈이 있다. 끝난 뒤의 상태는 맞지만 관리자 조회·전체 방 목록·메트릭처럼 실행 도중의 전체 모습이 필요한 기능은 따로 설계해야 한다. 클래스 본문(주석 포함)은 전체 락 64줄, 방마다 락 + 재확인 109줄이고, 후자에는 재시도 루프 3개와 규칙 4개(같은 객체 재확인, 락 안에서 그 객체일 때만 삭제, 세션 → 방들 매핑은 `compute`로 항목 단위 원자적 수정, 방 락을 잡은 채 다른 방 락을 잡지 않기)가 필요하다.

## 결정, 한계, 재검토 조건

전체 락 결정은 유지했다. 위 결과에서 방마다 락 + 재확인이 앞선 경우는 좁았고, 실제 서버에서 락 대기가 병목이라는 근거는 아직 없다. 반면 대가(규칙 4개, 실행 도중 전체 모습을 볼 수 없음)는 확인됐다.

- 한계: I/O 없는 반복 루프다. 실제 서버에서는 메시지 파싱·네트워크 I/O가 끼어 락을 잡는 비율이 훨씬 작으므로, 이 차이가 실제 처리량에 얼마나 드러날지는 P1-7 k6(부하 테스트 도구) 측정 전에는 모른다. 스레드 64개는 코어 8개보다 많아 OS 스케줄링 영향이 섞인다. 2회(첫 실행 포함 3회) 실행이고 통계적 검정은 하지 않았다.
- 재검토 조건: P1-7 k6 측정이나 이후 측정에서 방 관리자의 락 대기가 병목으로 확인되면 방마다 락 + 재확인으로 바꾸고 같은 경쟁 테스트로 검증한다.

## 배운 것

사용자가 정리 단계에서 남긴 문장(원문)은 이렇다.

> "세션, 방 서로간의 정합성을 보장된 매핑을 확인하기 위해 테스트를 진행 후 구현하였다. 정해야할 것은 락을 어느 위치에, 어떤 락을 선정할 것인지에 대해서였는데, 기준이 전체락을 할지, 방마다의 락과 재확인을 하는 방향으로 갈것인지에 대한 선택이었다. 두개 모두 진행하였고 실제로 방이 많고 입장/퇴장이 많은 경우에만 락과 재확인이 더 성능이 좋았다. 하지만 지금은 구현 초반이라 전체락으로 선택하였고 추후에 진행 예정이다."

> "락이 필요한 이유는 방찾기에서 락을 잡고서 다른 요청에서 방을 찾을때 변경되기 전에 변경유무를 알지 못해 정합성이 어긋나는 일이 발생될 수 있기 때문이다."

기록(plan)에는 이 문장들을 앞 절의 결과에 맞춰 보정한 내용도 남아 있다. 이득이 난 조건은 서로 다른 방에서 방이 유지될 때였고, 전환은 예정이 아니라 조건부다.

자기 코드에서 "확인 → 행동" 두 단계가 따로 호출되는 곳을 찾아보자. 동시성 컬렉션을 쓰더라도 그 사이에 다른 스레드가 끼어드는 타임라인을 그려 보고, 방어 없는 구현에서 먼저 실패하는 테스트를 만든다. 다음 글은 P1-4, 같은 방 브로드캐스트와 다른 방 격리다.

## 용어 정리

- 세션(`WebSocketSession`): 서버가 연결 하나를 표현하는 객체
- 방 관리자(`RoomRegistry`): 두 매핑을 가진 클래스
- 방 → 세션들 매핑 / 세션 → 방들 매핑
- 불변식: 언제나 참이어야 하는 조건(①~③)
- 입장(`JOIN`) / 퇴장(`LEAVE`) / 끊김(연결 종료, `removeSession`)
- 빈 방 삭제
- 경쟁(race condition)
- 전체 락: 방 관리자 전체에 락 하나(`synchronized`)
- 방마다 락 + 재확인: 방마다 락을 잡은 뒤 방 → 세션들 매핑의 방이 내가 쥔 바로 그 객체인지 다시 확인하고, 다르면 처음부터 다시
- 스냅샷: 두 매핑을 한 순간에 복사한 모습
